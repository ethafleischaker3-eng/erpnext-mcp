## 1. 目的

本总则用于将 MCP 改造拆分为可由 AI 独立理解、实施、自检和交付的封闭任务包，使每项工作满足：

1. 输入完整且版本确定；
2. 目标、授权范围和禁止事项明确；
3. 输出可检查，不依赖执行者自评；
4. 实施与正式验收相互隔离；
5. 失败能够定位到任务包、契约、实现或验收题；
6. 任何变更均可追踪其上下游影响。

任务包不是普通待办事项。缺少前置条件、权威输入、完成定义或验收方式的工作，不得标记为封闭任务包。

## 2. 基本原则

### 2.1 单一目标

一个任务包只交付一个边界清楚的成果。不得把接口摸底、契约设计、业务实现和正式验收混入同一任务包。

### 2.2 输入冻结

任务包进入实施前，其权威输入、版本、目标、范围和完成定义必须冻结。执行者不得在实施过程中自行修改上游要求。

### 2.3 输出可判定

完成条件必须能通过文件检查、接口检查、测试或数据终态断言客观判定。不得使用“基本完成”“大致可用”“表现合理”等主观表述。

### 2.4 最小授权

任务包仅授予完成本任务所需的文件、环境、接口和数据权限。未明确授权的范围默认不可修改；需要扩大范围时必须停止并发起变更。

### 2.5 实施与验收隔离

实施任务包不得包含冻结验收题的具体内容、隐藏数据或期望终态。正式验收必须使用独立验收包，并同时满足会话上下文与工作目录权限隔离；执行者角色还须满足下述独立性要求。

同一任务包的 Implementer 不得兼任 Acceptor；验收题 Owner 不得参与针对该题目的实现、调参或修复。使用 AI 执行时，“独立”至少要求会话上下文与工作目录权限隔离，不能仅通过新开一个仍可读取隐藏题目的会话满足。

适用“隐藏题污染隔离”：任何读取过某一正式验收题正文、隐藏初始数据、评分细节或终态断言的自然人、服务主体、会话或执行实例，不得参与该题对应能力的实现、实施方案评审、调参或定向修复。实施 Reviewer 与验收 Reviewer 必须分离；验收侧向实施侧只能返回失败类别、未满足的公开契约/完成条件及必要的脱敏证据，不得返回可反推出隐藏断言的细节。

### 2.6 不静默假设

遇到权威输入冲突、环境事实不符、前置条件缺失或范围不清时，执行者必须停止相关工作并报告，不得以未经记录的假设继续实施。

### 2.7 编号稳定

任务包编号一经引用不得因排序调整而重排。新增任务包使用新编号；废弃任务包保留编号并标记状态，不得复用。

## 3. 权威输入及优先级

任务包必须列出适用的权威输入及精确版本。默认优先级由高到低为：

1. 《开源后端 Agent 化接入规范》；
2. 已冻结的《ERPNext-MCP 改造 PRD》；
3. 已评审并冻结的 MCP tool 契约；
4. 已确认的 ERPNext 业务动作—API 映射与实测记录；
5. 本总则；
6. 具体任务包；
7. 普通说明、笔记和未评审草稿。

低优先级材料不得改变高优先级材料的业务范围、安全约束或验收要求。发现冲突时，任务包状态转为“待澄清”，由有权修改对应上游文件的负责人处理。

## 4. 任务包体系

### 4.1 项目总控包

项目总控包维护全局信息，不直接承担业务实现，包括：

- 上游文件及版本；
- 项目目标、范围与非目标；
- 阶段、任务包及依赖关系；
- L3 客户端能力门槛；
- 操作允许清单与引用允许清单；
- 统一安全约束；
- 当前基线、变更记录和项目状态；
- 项目级完成定义。

### 4.2 调研与验证任务包

用于确认外部事实，例如客户端确认能力、ERPNext API 行为、事务边界、权限和回滚路径。其输出必须是可复核的实测记录，不得直接以推测作为结论。

### 4.3 契约设计任务包

用于冻结 tool 名称、description、输入输出 schema、annotation、错误结构、权限、幂等、断言和批次行为。契约冻结后，实施任务包只负责实现，不得临场改变业务语义。

### 4.4 实施任务包

用于实现一个公共能力或一条业务闭环。每个实施包必须引用已冻结契约，并接入项目统一的权限、幂等、前置断言、事后校验和批次台账机制。

### 4.5 验收任务包

用于独立运行冻结任务集、恢复初始快照、检查终态并计算指标。验收包不得被实施执行者修改；验收失败不得通过降低断言或改写题目来规避。

### 4.6 交付任务包

用于汇总符合性声明、验证记录、权限矩阵、部署运维说明、回滚手册、验收报告、已知限制及二期事项。

## 6. 封闭任务包的必备结构

每个任务包必须完整包含以下部分。

### 6.1 基本信息

- 任务包编号与名称；
- 版本；
- 当前状态；
- 创建人；
- Owner（任务结果负责人）；
- Implementer（实际实施执行者）；
- Implementation Reviewer（输入与实施方案评审人，不得读取对应隐藏验收材料）；
- Acceptance Reviewer（如需审阅隐藏验收材料；不得参与对应实现、实施方案评审、调参或定向修复）；
- Acceptor（独立验收人）；
- 创建、冻结和完成日期；
- 上游任务包与下游任务包。

任务包进入“待评审”前必须检查角色隔离：Implementer 与 Acceptor 必须为不同的自然人、服务主体或上下文隔离且权限独立的执行实例；Implementation Reviewer 不得读取对应隐藏验收材料；读取过隐藏材料的 Acceptance Reviewer 不得参与对应实施评审。不满足时不得冻结。Implementation Reviewer 可以兼任 Owner，但不得因此替代独立验收。

### 6.2 目标

用可观察的业务或工程结果描述任务完成后的状态。目标应说明“完成后得到什么”，而不是笼统描述“开展什么工作”。

### 6.3 非目标

明确本任务不解决的事项，防止执行者顺手扩大范围。

### 6.4 前置条件

列出任务开始前必须成立的事实，包括上游包状态、文件版本、环境、数据快照、凭证、能力验证和依赖服务。任一强制前置条件不成立，任务不得进入“实施中”。

### 6.5 权威输入

列出文件、记录、契约和环境基线的名称、路径、版本或提交标识。仅写“参考相关文档”视为不合格。

### 6.6 授权范围

必须明确：

- 可读取的文件与目录；
- 可修改或新增的文件与目录；
- 可调用的系统、接口和命令；
- 可使用的数据与凭证类型；
- 是否允许改变数据库状态；
- 是否允许安装依赖或改变运行环境。

授权范围还必须列出本包的写入集、共享文件及其所有权。共享文件没有明确 Owner 或协调规则时，不得由多个任务包并行修改。

### 6.7 禁止事项

至少包含适用于本任务的以下约束：

- 不得修改上游规范、冻结 PRD 和冻结验收题；
- 不得扩大业务对象或权限范围；
- 不得新增通用 CRUD 或任意代码执行面；
- 不得绕过 server 侧确认；
- 不得让失败路径静默成功；
- 不得输出密钥、密码、完整堆栈或未授权业务数据；
- 不得为通过验收而改变冻结题目。

### 6.8 工作项

将工作拆成有限、明确、可核验的事项。每项必须对应至少一个交付物或完成断言。

### 6.9 输入输出契约

涉及 tool 或接口时，必须引用或写明：

- 名称和业务语义；
- 输入与输出 schema；
- annotation；
- 前置断言；
- 幂等边界；
- 事后校验；
- 错误与自纠建议；
- 批次及审计行为；
- 自主度档位和确认要求。

### 6.10 不变量

列出任何正常路径、失败路径和重试路径都不得破坏的规则。项目级不变量至少包括：

- 两张允许清单之外的对象不可被操作或引用；
- 引用允许对象不可经 MCP 增删改；
- 人确认操作未经有效确认不得写入；
- 按 B05 冻结的“同一业务意图”判定规则，重复重试最多产生一次业务变化；B05 未冻结前不得擅自使用会话、请求 ID 或传输层字段代替该规则；
- 独立的合法重复业务不得被幂等机制合并；
- 写操作成功响应前必须完成事后回读；
- 普通调用方不得读取其他调用方的批次信息；
- 后端不可达时不得自动重试写操作；
- 错误不得以成功响应伪装。

### 6.11 交付物

逐项列出必须提交的文件、记录、配置、报告或可运行能力，并注明路径或存放位置。

### 6.12 开发自检

列出执行者可见且允许执行的检查，包括静态检查、公开测试、接口验证和数据库终态检查。自检通过不等于正式验收通过。

### 6.13 证据清单（Evidence Manifest）

每个任务包必须维护统一证据索引。每条证据至少包含：

- 证据编号；
- 对应的工作项、完成条件或断言；
- 执行者与执行时间；
- 环境、客户端、SDK、后端及关键依赖版本；
- 实际执行命令或人工操作步骤；
- 退出码或明确的成功/失败状态；
- 结果摘要和原始输出位置；
- 代码提交标识、文档版本或数据快照标识（适用时）；
- 敏感信息脱敏说明。

证据清单不得记录密码、密钥、完整认证头或其他敏感凭据。仅粘贴结论而无可复核来源，不构成有效证据。

**治理生效前存量证据接管规则**：

- 总则冻结及 P00 建立前产生的探索记录只能标记为“治理生效前探索证据”，不得直接视为某任务包的正式完成证据；
- 对 PRD 已引用为“B00 实测”的版本、公司、币种、价格表等事实，B00 启动后必须在相同或明确记录差异的环境中重新执行验证，或由 B00 Implementation Reviewer 检查原始输出、执行时间、环境/版本标识和可复现性后书面采纳；
- 重新验证或正式采纳的结论必须取得新的证据编号，录入 B00 Evidence Manifest，并保留对原探索记录的来源引用；
- 缺少原始输出、环境标识、执行主体或无法复现的探索结论不得采纳，必须重新验证；
- 证据接管只确认事实，不追认治理生效前未获授权的状态变更，也不得绕过 B00 的其他完成条件。

### 6.14 完成定义

完成定义必须逐条可判定，至少覆盖：

- 所有交付物存在且内容完整；
- 工作项全部完成；
- 输入输出契约未被擅自改变；
- 适用的不变量均有验证证据；
- 开发自检通过；
- Evidence Manifest 完整且能够逐项追溯完成条件；
- 未修改禁止范围；
- 已记录剩余限制和风险；
- 独立验收通过，或按任务性质明确不适用。

### 6.15 停止与升级条件

出现下列情况时必须停止受影响工作并报告：

- 权威输入互相冲突；
- ERPNext 实际行为与冻结事实记录不一致；
- 需要新增对象、tool、权限或外部依赖；
- 必需对象不在允许清单；
- 无法满足确认、幂等、回滚或最小权限要求；
- 需要修改冻结验收题；
- 操作可能影响生产或非授权数据；
- 无法客观证明完成定义成立。

报告必须包含阻断事实、影响范围、已完成的安全检查以及需要谁作出什么决定。

## 7. 状态流转

任务包统一使用以下状态：

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 规划中 | 已登记稳定编号，但尚未形成完整任务包文件 | 已确认存在该任务需求与初步依赖 |
| 草拟 | 已形成任务包文件，内容尚可调整 | 已创建完整任务包文件，并指定至少一个 Owner |
| 待评审 | 等待检查完整性与可执行性 | 必备结构完整 |
| 已冻结 | 输入与完成定义不可自行变更 | 评审通过并记录版本 |
| 实施中 | 正在执行 | 所有强制前置条件满足 |
| 待验收 | 实施和自检完成 | 已提交全部交付物与证据 |
| 已通过 | 独立验收通过 | 所有完成条件成立 |
| 退回 | 验收未通过，可修复 | 有明确失败项和责任层级 |
| 待澄清 | 因冲突或缺失无法安全继续 | 触发停止条件 |
| 已废弃 | 不再执行 | 有替代包或范围变更记录 |
| 已封存 | 完成且材料归档 | 已通过并完成影响登记 |

“规划中”进入“草拟”必须先创建任务包文件并指定至少一个 Owner。不得从“草拟”直接进入“实施中”，不得在“实施中”静默改变冻结内容。

允许的主流转为：

```text
规划中 → 草拟 → 待评审 → 已冻结 → 实施中 → 待验收 → 已通过 → 已封存
```

异常与恢复流转：

- `待评审 → 草拟`：评审发现结构或内容不完整；
- `实施中/待验收 → 退回`：实现、自检或验收未满足冻结要求；
- `退回 → 实施中`：冻结输入、契约、范围和完成定义均未变化，仅在原授权内修复实现；须登记新的实施尝试及回归范围；
- `退回 → 待评审`：需要修改任务包、契约、权限、范围或完成定义；必须先升版并完成影响分析，不得沿用旧冻结状态；
- `任一未封存状态 → 待澄清`：触发停止条件；澄清未改变冻结内容时返回原状态，改变冻结内容时升版后进入待评审；
- `规划中/草拟/待评审/已冻结/待澄清 → 已废弃`：有决策记录并明确替代包或范围变更；
- `已通过 → 已封存`：归档材料和影响登记完成。

每次状态变化都必须写入任务包的“评审与状态记录”并同步登记表；不得覆盖历史记录。

### 7.1 仪式档位（三档）

任务包按业务写入风险与是否接触隐藏验收材料分为三档，档位决定其在“已冻结”之后强制经历的环节强度；档位在登记表任务行备注列标注，冻结时随任务包一并评审。

| 档位 | 强制环节 | 适用说明 |
|---|---|---|
| 档 1 轻量 | 冻结 → 实施 → 自检 + Implementation Reviewer 记录评审 | 纯设计/文档/只读类，无数据库写入且不接触隐藏验收材料；不强制独立验收、不强制封存与下游影响记录，其正确性由下游首次使用时验证 |
| 档 2 标准 | 冻结 → 实施 → 独立验收 | 基础设施或只读能力（含幂等、断言校验、批次台账等通用安全机制），需客观验证但写入风险低；封存可合并，不强制逐包下游影响记录 |
| 档 3 完整 | 冻结 → 实施 → 独立验收 → 封存 + 下游影响记录 + Freeze Manifest | 写业务数据、直接管控越权面的安全底座（权限/允许清单/人工确认）或集成验收，维持第 8–15 节全流程不变 |

档位不改变第 8 节冻结规则与第 12 节变更控制；任何档位的任务包冻结仍需 Freeze Manifest 记录输入版本与完成定义。档 1/档 2 不强制单独封存，其终态为“已通过”，封存与下游影响记录合并入 P00 总控或直接下游的封存环节。验收区任务（C01b、G01 等）按第 16.2 节门槛执行，不适用本档位。

## 8. 冻结规则

任务包冻结时必须记录：

- 任务包版本或提交标识；
- 全部权威输入版本；
- 完成定义；
- 评审结论；
- 已知风险；
- 上下游依赖；
- 验收责任人。

任务包登记表只冻结字段结构、编号规则、状态枚举和更新规则，不冻结持续变化的任务行内容。任务行的状态、责任人、版本、位置及证据位置可以按本总则受控更新，但每次更新必须在对应任务包状态记录或 P00 总控记录中留下时间、操作人和依据。任务范围、依赖、写入集或所有权的实质变化仍须执行第 12 节变更控制。

冻结后，文字润色且不改变语义的修改可作为补丁记录；任何影响范围、契约、不变量、权限、数据或验收结果的修改都必须升版本并执行影响分析。

## 9. 实施规则

实施执行者开始前必须先完成以下动作：

1. 阅读任务包及全部权威输入；
2. 核对任务包版本和前置条件；
3. 检查工作区是否包含非授权变更；
4. 声明计划采用的任务边界；
5. 确认正式验收题对实施会话不可见。

实施期间必须：

- 仅在授权范围内工作；
- 保留用户或其他任务包已有的无关修改；
- 记录关键假设、实测事实和偏差；
- 先完成公共机制接入，再宣称业务能力完成；
- 对每项完成定义提供证据；
- 遇到停止条件立即停止相关操作。

## 10. 实施与验收的物理隔离

项目至少划分两个相互隔离的区域：

### 10.1 实施区

允许包含：

- 上游规范与 PRD；
- 已冻结 tool 契约；
- 接口事实记录；
- 实施任务包；
- 实现文件；
- 公开开发自检。

不得包含：

- 正式验收题全文；
- 隐藏初始数据；

- 隐藏终态断言；
- 正式评分脚本的判定细节。

### 10.2 验收区

包含：

- 冻结任务集；
- 初始数据与快照；
- 重置工具；
- 终态断言；
- 评分规则；
- 验收运行记录。

实施执行者不得修改验收区。正式验收必须使用与出题不同的会话，并以系统和数据库终态为准，不接受 agent 自评。

## 11. 验收规则

验收开始前必须确认：

- 任务包和验收题版本均已冻结；
- 验收环境独立于生产；
- 初始快照可恢复；
- 被测 agent 未获得出题会话上下文；
- prompt、客户端和运行环境版本已记录；
- L3 所需客户端确认能力已经验证。

验收失败时必须将原因归入以下一类：

1. 实现不符合冻结契约；
2. tool 契约不足以支持真实业务任务；
3. 环境或初始数据不正确；
4. 验收题违反后端实际业务语义；
5. 上游 PRD 或规范冲突。

默认修改实现或 tool 契约，不得修改冻结验收题。只有验收题本身违反后端实际业务语义时才允许修题，并必须记录证据、升版本且废止旧结果。

## 12. 变更控制与影响分析

任何冻结后变更必须形成记录，至少包含：

- 变更原因；
- 变更前后内容；
- 证据与决策人；
- 受影响的任务包、契约、测试和验收结果；
- 是否需要重新冻结；
- 是否需要重新实施或重新验收。

出现以下变更时，相关历史验收结果自动失效：

- PRD 业务范围或自主度档位变化；
- tool 业务语义、输入输出或 annotation 变化；
- 允许清单或权限模型变化；
- 幂等、确认、断言、回滚机制变化；
- 冻结验收任务集发生实质修改；
- 被测客户端、模型或固定 prompt 的变化影响可比性。

## 13. 依赖与并行规则

任务包只有在不存在共享写入冲突、且所需上游均已冻结时才能并行。以下工作不得倒置：

- 通用执行面判断先于后端侧准备；
- B00 后端基础能力准备先于 A01 客户端确认能力核查；
- A01 必须在后端侧准备之后、任何正式业务 tool 开发之前完成；只允许为核查开发隔离的最小确认能力探针；
- ERPNext 接口事实确认先于对应 tool 契约冻结；
- C01a 盲出题先于 D02 业务 tool 契约冻结；D01 公共契约与错误模型不含业务语义，可与 C01a 并行，但同样不得读取 C01a 的题目正文、隐藏数据或终态断言；C01b 的覆盖审查与最终冻结先于正式业务实现；
- C01a 只能读取后端源码/数据模型、冻结的源码版本基线和上游规范第 8 章。B00 仅可作为环境与源码版本就绪的启动门槛；C01a 不得读取 B01～B05 的接口结论、MCP 契约、server 实现或既有验收断言；
- D01/D02 可以确认 C01a 已完成及其版本标识，但不得读取 C01a 的题目正文、隐藏数据或终态断言。C01b 作为验收区任务可以读取 C01a 产物与冻结的 D02 契约，仅用于覆盖映射、补题和可解性验证，不得把隐藏题目反馈给实施区；
- C01b 发现覆盖缺口时，可启动新的盲出题轮次；补题会话仍只能接触源码/数据模型与规范第 8 章，不得接触 MCP server 实现或冻结契约；
- tool 契约冻结先于对应实现；
- B05 幂等可实现性调研形成可评审结论前，E02 不得冻结或实施；
- E02（幂等、断言校验与批次台账）仅以 B05 结论与 B00 身份结论为前置，可在 D02 冻结前设计并冻结；其“接入具体 tool”阶段须待 D02 契约冻结后按冻结契约落地；
- E01（权限、允许清单与人工确认）仍以 D02 冻结契约为前置，不得在 D02 冻结前冻结或实施；
- B01～B04 必须实测 confirm 关键状态校验、乐观版本断言与后端事务/原子提交能力；对应结论形成前，D02 不得冻结相关 confirm 契约；
- B00 必须确定可信调用方身份的来源、稳定性、服务账号共享策略以及管理员/普通调用方区分原则；E02（批次台账部分）在此基础上冻结批次 Owner 持久化、跨会话查询和授权契约；
- B00 只负责验证后端能否按调用方粒度配置权限，并建立核查/探针所需的临时最小权限；E01 负责依据冻结 tool 契约形成正式业务角色、权限矩阵和两张允许清单，并完成越权验证；
- B00 的权限核查结论是 E01 的权威输入。E01 不得直接沿用临时探针权限作为正式业务权限，必须按冻结契约重新审查、配置和验证；
- 公共安全底座先于依赖它的业务写 tool 完成；
- 单项自检先于集成验收；
- 集成验收先于项目交付。

并行任务包不得同时修改同一冻结契约或同一核心文件；确需共享时，应先拆分所有权或改为串行。

## 14. 任务包退回规则

验收退回记录必须包含：

- 失败的任务包版本；
- 未满足的完成定义或断言；
- 实际结果与期望结果；
- 失败分类；
- 是否影响其他已完成任务包；
- 建议修复范围；
- 修复后需要执行的回归范围。

修复不得超出原任务包授权范围。若修复需要改变契约、权限、对象范围或验收题，必须先走变更流程。

## 15. 任务包封存与项目追溯

### 15.1 固定存放位置

以项目根目录为基准，治理材料使用以下固定位置：

- 具体任务包：`docs/task-packages/<任务包编号>/task.md`；
- 任务包公开 Evidence Manifest：`docs/task-packages/<任务包编号>/evidence-manifest.md`；
- 任务包变更记录：`docs/task-records/changes/<变更编号>.md`；
- 任务包退回记录：`docs/task-records/returns/<退回编号>.md`；
- 冻结清单及文档哈希：`docs/task-records/freeze-manifests/<文档名>-<版本>.md`；
- P00 项目总控状态与登记表：`docs/task-packages/P00/` 与 `docs/任务包登记表.md`。

原始证据、凭据、包含敏感信息的日志以及正式验收隐藏材料不得因上述路径约定进入公开实施区；其实际受控位置必须在 Evidence Manifest 中登记脱敏引用。验收材料的位置和访问控制以《实施区与验收区边界》为准。

### 15.2 封存内容

任务包通过后应封存以下材料：

- 冻结版任务包；
- 权威输入版本清单；
- 交付物；
- 自检记录；
- 独立验收记录；
- 变更与退回记录；
- 已知限制；
- 对下游任务包的影响说明。

任何最终业务能力都应能够反向追溯到：

```text
业务能力
→ tool 契约
→ 实施任务包
→ 代码或配置交付物
→ 开发自检
→ 冻结验收题
→ 终态断言与验收结果
→ 上游 PRD 条款
```

## 16. 项目级门槛

### 16.1 L3 门槛

B00 未通过前不得启动 A01。客户端 server 侧确认能力验证记录未通过评审前，不得开发任何正式业务 tool，不得正式验收或对外宣称 L3。允许使用隔离的最小探针完成能力核查，不得将探针结果代替业务 tool 验收。核查不通过时，所有写操作 tool 均只能返回 plan，不得保留全自动写入。

### 16.2 实施门槛

对应 ERPNext 接口事实、C01b 最终冻结的验收任务集和 tool 契约未准备完成前，不得启动正式业务实现任务包。B05 未形成可评审的幂等结论前，不得冻结或实施 E02。

PRD 中具体币种、默认 selling Price List、身份模型、幂等方案和 confirm 原子性仍标记待验证时，只允许执行负责取得这些事实的 B00/B01～B05；不得冻结依赖这些事实的 D/E/F 任务包。

P00 未明确 Owner、实施区与验收区实际路径未填写、访问控制未验证或 Evidence Manifest 未记录隔离证据时，不得启动 C01a、C01b、G01 或任何会接触正式验收材料的任务。路径存在但实施会话仍可读取隐藏验收材料，视为隔离未生效。

### 16.3 写操作门槛

权限与允许清单、幂等、前置断言、事后校验、批次台账以及适用的确认机制未接入并验证前，写 tool 不得标记完成。

### 16.4 项目完成门槛

只有在冻结任务集连续达到 PRD 指标、失败路径全部通过、符合性材料齐备且所有阻断问题关闭后，项目才可标记完成。

### 16.5 后续任务启动门槛

本总则 v1、任务包模板、登记表的字段结构/编号与更新规则及记录模板必须先独立完成评审冻结，并建立 P00 总控包。其后方可创建并冻结 B00；B00 通过后方可创建并冻结 A01。B00 与 A01 不属于本总则自身冻结的前置条件，而是后续项目任务启动的顺序门槛。

## 17. 本总则的完成定义

本总则投入使用前，应确认：

- 项目负责人认可任务包分层与状态流转；
- 实施区与验收区的边界规则已经评审；实际路径和访问验证可作为 B00 交付物完成，但在其完成前不得启动验收相关任务；
- 任务包模板已经建立；
- 任务包登记表能够记录编号、版本、状态、依赖和责任人；
- 变更记录和退回记录采用第 15.1 节的固定存放位置，目录可写性由 P00 建立时验证。

在上述条件全部满足并形成项目负责人评审记录前，本总则状态只能为“待评审”，不得标记为“已冻结”或“已投入使用”。总则冻结后按照 §16.5 依次建立 B00、A01；它们的执行反馈如需改变总则，应另行发起版本变更，不影响总则 v1 已完成的合法冻结。

本总则一经评审冻结，后续调整须按第 12 节执行变更控制。
