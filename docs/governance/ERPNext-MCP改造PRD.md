## 1. 背景与目标

### 1.1 背景

ERPNext 是本规范的第一个落地实例。本次将 ERPNext 进销存核心域封装为 MCP tool 面，验证「旁挂 MCP server → 通用 agent 读写管理」的完整闭环。本 PRD 只回答「这次做什么」（§3.4）。

### 1.2 目标

通用 agent 经 MCP 对纳入范围对象完成三类能力：

| 能力 | 含义 |
|---|---|
| 读 | 检索单据与主数据、查看单据详情与状态、查询库存余量与流水 |
| 写 | 创建/维护主数据（客户、供应商、物料、价格），创建交易单据草稿 |
| 管理 | 单据生效与取消、库存调拨、盘点调整方案 |

「管理」指业务数据管理（单据生命周期与库存），不含系统管理（用户/角色/站点设置），后者明确不接（见 2.2）。

终态对齐 §6.3：agent 自主 plan 完成「接单 → 备货 → 发货 → 盘点建议」类多步任务，无需逐步人工喂指令。

### 1.3 分级验收口径

客户端能力核查结果决定实际验收形态，L3 与 L2 受限形态不得共用同一写入终态断言，也不得混用验收结论。

| 验收项 | L3（核查通过） | L2 受限形态（核查不通过） |
|---|---|---|
| 只读 tool | 返回值满足冻结断言 | 返回值满足冻结断言 |
| 原全自动写 tool | 执行真实写入，终态满足数据库断言 | MUST NOT 写入；返回可执行 plan，数据库终态保持不变 |
| 原人确认写 tool | 确认后写入并满足终态断言；拒绝时不写入 | MUST NOT 写入；返回可执行 plan，数据库终态保持不变 |
| 只出 plan tool | plan 满足客观断言且不写入 | plan 满足客观断言且不写入 |
| 失败路径 | §12.3 五类全部通过 | 适用于该形态的五类失败路径全部通过；所有写入尝试额外断言零写入 |
| 可宣称能力 | 可稳定读取、写入和管理 | 可稳定读取并生成写入/管理方案；MUST NOT 宣称已完成实际写入或管理闭环 |

plan 的客观断言至少覆盖：拟执行动作、目标业务对象、关键字段与数量、执行顺序、前置条件、确认/风险提示；不得以 agent 自评“方案合理”作为通过依据。

两种形态共同要求：

1. 依 §12 生成并冻结任务集，使用通用 agent 且不改固定 prompt，终态或零写入状态与对应形态断言一致。
2. L3 覆盖每个写 tool ≥1 题及三个启用档位；L2 受限形态对每个原写能力至少覆盖 1 道 plan/零写入题，并覆盖实际启用的只出 plan 档。
3. 至少包含一条完整销售多步链和一条完整采购多步链。L3 断言最终单据、库存与流水；L2 断言完整方案及数据库全程无写入。
4. agent 调用成功率连续两轮达到第 6 节验收线，失败路径题通过率 100%。

只有 L3 三类写入断言全部满足，才可宣称“接口已改造为 MCP 可稳定调用、读写、管理”。

### 2.2 明确不接

财务（销售发票、收款/付款、记账凭证及总账）、制造（BOM、工单、生产计划）、CRM、HR、项目、资产、网站内容、系统管理（用户、角色、权限、站点设置）。以上对象不得被选作 tool 的目标对象，不得出现在对象类型选择字段、可写字段或 Link 字段的目标类型中，也不得被 tool 隐式创建、修改或删除。普通文本字段中偶然出现同名词语不构成越界。

理由：首个迭代聚焦进销存最小闭环，完整覆盖 1.2 三类能力且风险可控；财务与制造留待二期（见第 8 节决议 6）。

### 2.3 裁剪执行（操作允许清单 / 引用允许清单）

对象裁剪拆成两张清单，均在 server 侧强制执行：

- **操作允许清单**（§2.1 的 12 类对象）：允许 agent 经明确授权的 tool 对其执行文档规定的业务动作（各对象实际读写能力以 §2.1「读写」列与 §3.3 tool 清单为准）。
- **引用允许清单**（依赖对象）：只允许作为业务 tool 的参数引用（用于前置断言校验、单据 link 字段），**不允许**经 MCP 直接创建、修改、删除；由 server 配置或后端预置。

引用允许清单（依赖对象）：Company、Warehouse、Price List、Currency、Customer Group、Supplier Group、Territory、Item Group、Unit of Measure。

> 操作允许清单外对象 MUST NOT 经任何 tool 读或写；引用允许清单对象只可被引用、不可被增删改。两张清单变更均走本 PRD 变更流程并重新验收。

**关联对象与子表边界**：

- Contact、Address 本期不纳入操作或引用允许清单；Customer/Supplier 等 tool 不得隐式创建、修改或删除 Contact、Address。
- Sales Order Item、Purchase Order Item、Purchase Receipt Item、Delivery Note Item、Stock Entry Detail、Stock Reconciliation Item 等必要单据子表，只能作为其父单据 tool 的嵌套行项目结构读写，不视为新增独立操作对象，不得作为 `target_object` 独立查询或修改。
- 所有可写字段及 Link 字段允许目标必须在 D02 契约中逐项冻结；server 不得接受任意字段名或任意 DocType。

## 3. tool 划分

### 3.1 通用执行面判断（§7.1 第一步）

候选三类：① 脚本引擎（需管理员启用，任意代码执行）；② 服务器本地命令行（非 API 形态）；③ 面向任意对象类型的通用增删改查接口（无业务语义）。

判定：① 违反 §9.6 窄接口与最小权限；② 不满足 §6.2 旁挂形态；③ 直接包装违反 §8.4。

**结论：不存在可作为 tool 执行面的通用执行面，按 §7.1 走「按业务任务拆分结构化 tool」路线。** 通用查询能力仅在 tool 实现内部复用，不改变划分结论。

### 3.2 命名方案

前缀命名空间 + 资源分组 + 统一动作后缀：`erpnext_<资源>_<动作>`。

- 选资源分组的理由：同一业务对象的动作聚簇，agent 按对象定位 tool 路径最短；动作后缀与档位规则一一对应（create=草稿、confirm=生效、cancel=取消、plan=只出方案）。
- 命名方案属验收迭代可调项（§8.2）：跑题显示选错率集中时，优先调前缀/后缀，不动 tool 语义。
- description 与参数名用通用业务语言，ERPNext 专有概念不出现在其中（§8.7）。

## 4. 写操作与档位归属

### 4.1 分组推导（依据 §10.2 三条，任一不满足即降档）

| 组 | tool（见 3.3 #） | ① 可逆 | ② 动主数据 | ③ 客观标准 | 档位 |
|---|---|---|---|---|---|
| 草稿创建 | 13、16、19、21、23 | 满足（草稿可删，批次回滚） | 否（仅引用主数据） | 满足 | **全自动** |
| 生效 | 14、17、20、22、24 | 不满足（冲回产生不可擦除流水，重建走新单） | 否 | 满足 | **人确认** |
| 取消 | 15、18 | 不满足（作废已生效单据，冲减库存/预留） | 否 | 满足 | **人确认** |
| 主数据 | 6–12 | 部分 | 是（全系统引用源） | 满足 | **人确认** |
| 盘点 | 25 | 不满足（覆盖库存基线） | 否 | 不满足（正确值是系统外事实） | **只出 plan** |

代表性推导两例：

**erpnext_sales_order_create（#13）**：① 产物为草稿、未生效、批次内可删——可逆，满足；② 客户/物料/价格均为引用，不产生主数据变更——满足；③ 建单结果与行项目字段均可写成可执行断言——满足。三条全满足 → 全自动。

**erpnext_stock_reconciliation_plan（#25）**：① 盘点覆盖实际库存基线，冲回需再次盘点，无确定性回滚——不满足；② 调整的是库存量而非主数据——满足；③「正确库存」取决于线下盘点，系统无法客观判定——不满足。两条不满足 → 只出 plan。

### 4.2 等级结论与 L3 门槛

启用档位：全自动、人确认、只出 plan 三档并存，存在全自动档写 tool → 本次接入 **暂定 L3**。人确认档可用性以 §7.3 客户端能力核查结果为准，降级路径见第 0 节。

**L3 门槛（§7.3 核查的验收条件）**：

- 客户端确认能力验证记录完成并通过评审前，本项目 MUST NOT 进行正式 L3 验收或对外宣称 L3。允许开发并运行隔离的「确认能力探针 / 最小测试 tool」以完成核查，但不得作为正式业务 tool 验收依据。
- 验证记录 MUST 由接入方确认有效，并纳入最终符合性材料（§3.5）。
- 验证不通过时：所有写操作 tool（包括原定全自动草稿创建和人确认操作）MUST 拒绝执行写入并 fail closed，仅返回 plan 或可自纠错误；只读 tool 可正常使用，整体符合性等级上限为 L2 受限形态。
- 「降级」语义：不通过时，本 PRD 中所有写操作的执行能力统一停用并按「只出 plan」运行，不得保留任何全自动写入；否则只要仍存在一个全自动写 tool，依据 §3.2 仍属于 L3。

## 5. 保障机制实现约定

双层要求（对内实现 + 对外声明）遵循 §9.1；本节只写 ERPNext 侧的实现口径。

### 5.1 幂等指纹（§9.3）

| tool 组 | 进指纹参数 | 排除参数 | 窗口期 |
|---|---|---|---|
| 主数据 create（#6、#8、#10） | 对象类型 + 按稳定顺序归一化的全部业务有效输入（名称、分类属性及其他影响落库终态的允许字段） | 不影响业务终态的展示性备注 | 由 B05 冻结；24h 仅为调研初始假设，不构成本版冻结契约 |
| 主数据 update / 价格（#7、#9、#11、#12） | 对象标识 + 按稳定顺序归一化的字段名及目标值 | 未变更字段 | 由 B05 冻结；24h 仅为调研初始假设，不构成本版冻结契约 |
| 订单草稿 create（#13、#16） | 实际生效的公司、币种、价格表 + 交易对手 + 要求日期 + 按稳定顺序归一化的行项目（物料、数量、单位、单价、仓库等全部影响终态的字段） | 不影响业务终态的展示性备注 | 由 B05 冻结；24h 仅为调研初始假设，不构成本版冻结契约 |
| 收货/发货草稿 create（#19、#21） | 实际生效的公司、币种 + 来源单据及来源行 + 要求日期 + 行项目（物料、数量、单位、仓库等全部影响终态的字段） | 不影响业务终态的展示性备注 | 由 B05 冻结；24h 仅为调研初始假设，不构成本版冻结契约 |
| 调拨草稿 create（#23） | 实际生效的公司 + 源仓、目标仓 + 行项目（物料、数量、单位等全部影响终态的字段）+ 过账日期 | 不影响业务终态的展示性备注 | 由 B05 冻结；24h 仅为调研初始假设，不构成本版冻结契约 |
| confirm / cancel（#14、#15、#17、#18、#20、#22、#24） | 目标单据编号 + 动作 | — | 由 B05 冻结；1h 仅为调研初始假设，不构成本版冻结契约 |

指纹由 server 依业务参数规范化计算，agent 不感知（§9.3）。窗口期内命中指纹：返回首次结果并附「重复请求已按幂等合并」。confirm 与 cancel 分别使用符合其合法前态的状态断言兜底：confirm 仅接受草稿状态，cancel 仅接受已生效状态；窗口期用于并发与重试。

> **需求口径已冻结，幂等实现契约尚待 B05 冻结**：server 必须同时防止同一业务意图的重试造成重复写入，并控制合法同参数业务被误合并的风险；在没有可信关联信号时，两者无法仅凭相同业务参数可靠区分。B05 完成前，不得宣称该矛盾已经解决，不得冻结或实施 E02。

**B05 必须形成的证据与决策**：

- 实测目标客户端、MCP SDK 和传输方式是否自动重试 `tools/call`，以及超时、断线和重连时的行为。
- 确认可被 server 可信观察且不由 agent 伪造的关联信号，并判断其是否违反“不绑定特定传输层字段”的上游约束。
- 若存在合规可信信号，冻结其生命周期及同一业务意图的判定边界；若不存在，必须在业务引用号、误合并策略、窗口期缩短或其他业务层方案中作出明确选择并记录残余风险。
- agent 传入的随机 request id 或幂等键不得成为可信覆盖值；有效负载不同不得命中同一指纹。
- B05 结论必须明确“同一业务意图连续调用只变更一次”和“合法重复业务如何表达”的可执行验收方法。

### 5.3 事后校验口径（§9.5）

- 每个写 tool 执行成功后，server 回读目标对象，断言期望终态字段（单据状态、行项目数量与价格、价格生效区间等）。
- 回读不一致 → 按 §8.6 报错、记入批次台账并标记待回滚；成功响应须符合声明的返回契约（§9.5）。

### 5.4 回滚批次粒度与执行入口

- 一次 tools/call 一个批次，server 生成批次标识；单次调用产生的全部变更同批。
- 批次台账由 server 独立留存（参数指纹、涉及单据编号、时间、会话），不依赖后端。
- 回滚路径：草稿 → 删除；已生效 → 后端原生取消；已取消 → 终态不可回滚，台账如实标注。
- 跨 tool 的业务流（订单 → 收货 → …）不合并批次，聚合回滚为二期。

**回滚执行入口（区分「业务取消」与「异常回滚」）**：

- **业务取消**（MCP 业务 tool）：`sales_order_cancel`、`purchase_order_cancel` 由 agent 经 MCP 调用，走「人确认」档。
- **异常回滚**（管理员运维，非 MCP tool）：采购收货、销售发货、库存调拨无对应 cancel tool，其取消会牵动库存与下游单据，由**管理员运维执行后端原生取消**，不对 agent 开放；server 不提供 rollback tool。
- 入口与权限：异常回滚仅管理员可用，走运维脚本/后端原生 API，操作记入批次台账。
- 回滚前确认：异常回滚属破坏性操作，执行前须管理员显式确认（展示完整受影响单据，§9.7 精神）。
- 批次依赖顺序：跨批次按单据上下游倒序回滚（先下游后上游），台账记录批次间依赖。
- 结果记录：成功/部分成功/不可回滚状态均如实记入台账；部分成功须列出已完成与未完成项。
- agent 能力边界与可见范围：agent 只能通过 erpnext_batch_status_get（#26）查询归属于自身可信调用方身份的批次及状态（读），不能主动发起回滚；不得查看其他调用方的批次参数、涉及单据与回滚信息。管理员运维可查询全量台账。可信调用方身份模型尚待 B00 核查并由 E04 冻结契约，在该契约完成前不得宣称批次访问隔离能力成立。

**主数据与价格回滚路径**：

- Customer/Supplier/Item create：批次记录创建前不存在的证据；仅在目标未被其他对象引用且后端允许时删除。已被引用或删除会破坏完整性时，标记“不可自动回滚”并转管理员处置。
- Customer/Supplier/Item update：写入前保存本次允许变更字段的前镜像、对象版本和必要关联状态；回滚时仅在当前版本仍与本批次写后版本一致时恢复前镜像。发现后续修改时不得覆盖，转管理员处置。
- Item Price set：区分新增与修改/覆盖；新增价格在未产生冲突引用且后端允许时删除，修改/覆盖保存原价格、币种、价格表及生效区间前镜像并按版本恢复。
- 前镜像必须最小化、加访问控制并按保留期处置，不得无必要保存敏感字段。
- 所有自动回滚失败、并发冲突、下游引用或不可逆状态必须写入批次台账，列明影响对象、失败原因和人工处置建议。

**批次身份模型的待验证要求**：

- B00 必须确认调用方由哪个认证主体标识、该标识能否跨会话保持稳定，以及该标识是否由 server 可信获取而非 agent 自报。
- B00 必须确认多个调用方是否共用 ERPNext 服务账号，并明确服务账号与 MCP 调用方身份的关系；若共用服务账号，批次隔离必须由 MCP server 的独立可信身份层承担。
- B00 必须确认管理员与普通调用方的区分及授权来源。
- E04 必须据此定义批次 Owner 的持久化字段、新会话查询旧批次的归属证明、普通调用方与管理员的查询授权及审计规则。

### 5.5 事务边界（§7.2.4 落地）

单张单据的创建/生效/取消是否由后端原生原子完成，须由 B01～B04 实测确认。关键 confirm 状态校验必须与实际提交处于同一后端事务，或由具备等价原子保证的后端专用方法完成；不得以 MCP 层“先查询、后调用提交”的两个远程请求冒充同一事务。MCP 调用应携带预期 `modified`/版本进行乐观并发断言，后端原生提交校验作为最终防线。跨单据流程天然跨调用，MCP 侧不引入跨调用事务，一致性由前置断言 + 事后校验 + 批次台账承担（§9.1）。

### 5.6 窄接口与权限口径（§7.2.2、§9.6 落地）

- 窄接口三层落实：操作允许清单限定可操作对象范围、引用允许清单限定可引用依赖对象；专用角色限定权限范围；每个 tool 只暴露其业务动作所需参数与操作。
- 专用系统账号 + 专用角色，权限收敛到各操作允许对象按其声明能力所需的读/写权限（只读对象如 Bin、Stock Ledger Entry 仅授予读）+ 引用允许清单对象的读（供前置断言校验）；不授予用户、角色、设置与两张清单外对象的任何权限。
- 越权由后端原生权限拒绝，tool 转译为可自纠报错（§8.6）；验收任务集 MUST 含越权类题目（§12.3）。

### 5.7 验收环境（§12.4 落地）

独立站点，与生产数据隔离；以后端原生备份/恢复能力实现快照重置（满足 §6.1、§12.4）；每道写题配初始态快照与重置脚本（§12.2）。合成数据不进生产，验收环境 schema 与生产一致。

## 6. 指标阈值

| 指标 | 口径 | 阈值 |
|---|---|---|
| agent 调用成功率 | §13.1 | 首轮迭代 ≥ 80%；验收线 = 同一冻结任务集连续两轮 ≥ 90% |
| 失败路径题 | §12.3 五类 | 五类各至少 1 题，通过率 100% |
| 数据覆盖率 | §13.2 | 本次不适用（无治理） |

跨迭代比较遵守 §13.1 可比性限制；任务集重新生成或修改后，历史数据作废。

**可复算口径**：

- 分母：冻结任务集的全部自然语言任务数。环境故障导致任务未能有效执行时，该题标记为“环境无效”并修复环境后补跑；存在任何未补跑的环境无效题时，该轮不完整、不得计算正式成功率或形成验收结论。补跑必须使用同一任务集、固定 prompt、客户端/模型/server 版本和该题原始快照；无法保持可比性时整轮重新执行。
- 分子：一次任务同时满足选对 tool、参数正确、未违反安全/确认规则、在该题冻结的最大调用次数内结束，并通过对应形态的终态或零写入断言，才计为成功；任一条件失败均计 0。
- 一轮：将冻结任务集中的全部任务各执行一次。每题执行前恢复该题指定快照并验证初始态，执行后保存证据，再恢复或销毁该题环境；不得让上一题状态污染下一题。
- “轮次合理”：由 C01b 为每题冻结最大 tool 调用次数及允许的自纠次数，验收时不得临时调整。
- 连续两轮必须使用相同任务集版本、固定 prompt、客户端名称与版本、模型名称与版本/发布日期、MCP SDK 与 server 版本、关键配置及环境快照；任一影响可比性的变更均重新起算。
- 每轮报告必须给出任务总数、成功数、失败数、环境无效数、逐题调用次数、失败分类及计算公式，确保第三方可复算。

## 7. 边界处理

| 场景 | 处理 |
|---|---|
| 客户端不支持 server 侧确认机制 | 所有写操作 tool（含原全自动草稿创建）均拒绝写入并只返回 plan 或可自纠错误；只读 tool 正常使用，不得保留任何全自动写入 |
| 同业务意图重复调用 | 幂等指纹命中，返回首次结果 +「重复已合并」 |
| confirm 时单据非草稿 | 前置断言失败，返回当前状态与建议动作 |
| 库存不足（调拨/发货） | 报错含缺口数量与可用量，建议减量或换仓 |
| 主数据重名 | create 报错并指向 update；update 要求标识精确 |
| 越权（角色缺权限） | 转译报错列出所需权限，不透出堆栈 |
| 结果集超限 | 截断 + 分页与过滤提示（§8.5） |
| 单据被并发修改 | 报错建议重读后重试 |
| 后端不可达 | 明确报「后端不可达」；写操作不由 server 自动重试 |
| 参数缺失/格式错误 | 按 §8.6 返回可自纠报错 |
| 查询批次状态 | agent 可读、不可修改；由 erpnext_batch_status_get（#26）提供 |
| 异常回滚 | 仅管理员运维执行，MCP 不提供入口；结果（成功/部分成功/不可回滚）写入批次台账 |
