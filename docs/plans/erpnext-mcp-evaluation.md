# ERPNext MCP 一期技术评价与二期改造方案

## 1. 总体结论

ERPNext MCP 一期工程的目标基本达成。

项目围绕 ERPNext v15 的销售、采购和库存场景，完成了从 MCP Tool 定义、服务端实现、ERPNext 权限约束到集成验收的完整闭环。26 个 Tool 能够操作真实 ERPNext 数据，并非仅用于展示协议能力的概念 Demo。

一期的主要价值体现在三个方面：

1. 验证了通用 Agent 通过 MCP 管理 ERPNext 进销存业务的技术可行性。
2. 建立了相对清晰的 Tool 契约、业务边界和写操作安全机制。
3. 为二期扩展退货、经营分析、财务和制造领域提供了可复用的服务端框架。

一期当前应定性为：

> 一个边界清晰、机制较完整、经过系统验收的 ERPNext MCP 受控验收版，适合 PoC、内部试用和二期技术基线，但尚不具备直接作为企业生产系统上线的完整条件。

不应因为一期没有完成多用户身份、高可用、完整审计和企业级部署而否定其成果。这些能力属于二期生产化建设范围。但在相关能力补齐前，也不应把一期版本直接开放给真实企业用户执行高风险正式业务操作。

## 2. 一期工程评价

### 2.1 架构评价

一期采用旁挂式 MCP Server：

```text
MCP Client / Agent
        │
        │ stdio JSON-RPC
        ▼
ERPNext MCP Server
        │
        │ REST API + Token
        ▼
ERPNext v15
```

该架构选择总体合理：

1. 不需要侵入式修改 ERPNext 核心代码。
2. MCP Server 与 ERPNext 可以独立升级和部署。
3. Tool 层可以集中处理白名单、参数校验、幂等、确认和错误转换。
4. ERPNext 原生 DocType、状态机和权限机制仍然保留。
5. Agent 不直接接触任意 ERPNext API，降低了开放面的风险。

现阶段不足包括：

1. MCP Server 主要按单机 stdio 模式设计，不适合直接部署为共享企业服务。
2. 身份、批次和部分幂等信息依赖进程内存，服务重启后无法持续追踪。
3. Server 与固定公司、币种和价格表绑定，配置隔离能力不足。
4. 缺少标准安装包和完整初始化程序，部署过程仍然依赖实施人员理解 ERPNext 内部结构。

总体判断：

> 一期架构适合作为领域适配层基线，无需在二期整体推翻；二期应重点重构配置、身份、审计、传输和部署层，而不是重写全部 Tool。

### 2.2 业务范围评价

一期覆盖了进销存最小闭环：

| 领域 | 已覆盖能力 |
|---|---|
| 主数据 | 客户、供应商、物料、物料价格 |
| 销售 | 销售订单草稿、提交、取消、按订单生成发货单、发货生效 |
| 采购 | 采购订单草稿、提交、取消、按订单生成收货单、收货生效 |
| 库存 | 库存查询、库存流水、仓库调拨草稿、调拨生效 |
| 盘点 | 读取现状并生成盘点方案 |
| 通用查询 | 业务对象检索、单据详情、供应商检索 |
| 批次 | 查询当前 MCP 会话内的调用批次状态 |

这个范围选择是合理的：

1. 业务对象数量可控。
2. 覆盖真实库存变化。
3. 能形成销售和采购的端到端链路。
4. 高风险财务和制造能力没有过早纳入一期。
5. 盘点只生成方案，不直接调整账面库存，符合一期风险控制原则。

一期没有覆盖以下领域：

- 销售退货和采购退货
- 销售发票和采购发票
- 收款、付款和核销
- 总账和会计凭证
- BOM、工单、领料和完工入库
- 质量检验
- 跨对象经营分析
- ERPNext Workflow 审批
- 多公司、多币种和复杂价格策略

这些属于明确的能力边界，不应全部视为一期缺陷。

### 2.3 Tool 定义评价

一期共提供 26 个 Tool，整体定义有效。

Tool 的有效性体现在：

1. Tool 名称使用明确的业务动词，如 `create`、`confirm`、`cancel`、`query`、`get` 和 `plan`。
2. 创建草稿与提交生效分离，符合 ERPNext 的 `docstatus` 状态机。
3. 输入 Schema 限定了业务对象和字段，不接受任意 DocType、任意字段或任意 API 路径。
4. 更新和状态流转要求传入 `modified`，提供基础乐观并发保护。
5. 销售和采购订单不直接接受任意价格，价格由指定价格表解析。
6. 收货单和发货单要求关联来源订单，避免生成无来源业务单据。
7. 查询、草稿创建、正式提交和只出方案在 Tool 语义上有明确区分。
8. Tool 注解标识了只读、破坏性、幂等等属性，有利于客户端和 Agent 做调用决策。
9. 错误结果经过统一转换，不直接暴露后端异常和堆栈。
10. Tool 可以驱动真实 ERPNext 数据，已经完成实际 API 和 MCP 调用验证。

一期 Tool 设计中值得保留的模式：

```text
xxx_create
xxx_confirm
xxx_cancel
```

这一模式把“准备业务数据”和“产生正式业务效果”分开，是后续扩展退货、财务和制造能力时应继续采用的核心原则。

### 2.4 Tool 定义的不足

#### 2.4.1 通用查询能力偏基础

目前主要支持单对象搜索、单对象详情、库存余量和库存流水。真实企业还会需要：

- 订单履约进度
- 采购逾期和销售逾期
- 安全库存预警
- 呆滞库存和库存周转率
- 客户未交付金额
- 供应商交付表现
- 多仓库汇总
- 销售与采购趋势

如果继续由 Agent 通过多次基础查询自行聚合，会产生性能、分页遗漏和计算口径不一致问题。二期应增加服务器侧确定性聚合 Tool，而不是让模型自行计算全部经营指标。

#### 2.4.2 Tool 数量会随业务扩展快速增长

当前每个业务动作通常对应一个 Tool。对于一期 26 个 Tool 尚可管理，但扩展退货、财务和制造后，数量可能迅速超过 50 个。

二期需要建立 Tool 分域和命名规范：

```text
主数据域
销售域
采购域
库存域
财务域
制造域
分析域
运维与审计域
```

同时应评估：

- 哪些动作必须是独立 Tool
- 哪些能力适合合并为同一领域 Tool
- 哪些查询适合用固定报表 Tool
- 哪些内部实现不应暴露给 Agent

#### 2.4.3 MCP 确认不等于企业审批

当前 `elicitation` 能确认当前用户是否同意调用 Tool，但它不能替代 ERPNext Workflow。

企业审批通常包含发起人、审核人、批准人、部门、公司、金额阈值、信用额度、预算控制、审批意见和职责分离。

二期扩展财务和制造写操作时，必须把 MCP 确认与 ERPNext Workflow 分开定义：

```text
MCP 确认：用户同意 Agent 发起动作
ERPNext 审批：企业业务流程正式批准动作
```

#### 2.4.4 缺少正式的逆向业务 Tool

一期虽然支持部分订单取消，但取消不能替代真实退货。

真实退货通常需要：

- 关联原销售或采购单据
- 校验可退数量
- 生成退货单
- 产生反向库存流水
- 处理批次和序列号
- 处理退款、红字发票或贷项
- 保留原单和退货单之间的追溯关系

二期必须把“取消”和“退货”定义为不同业务能力。

### 2.5 安全机制评价

一期已经实现或设计了以下安全机制：

1. 专用 ERPNext 服务账号。
2. 专用最小权限角色。
3. DocType 级权限矩阵。
4. Server 侧对象白名单。
5. Server 侧字段白名单。
6. 人工确认类 Tool。
7. 客户端不支持确认时失败关闭。
8. 写能力运行前置检查。
9. 创建操作幂等。
10. 状态流转幂等。
11. 乐观并发令牌。
12. 写后回读终态。
13. 后端不可达时不自动重试写操作。
14. 错误输出脱敏和统一转换。

这些机制说明一期不是单纯的 API 包装器，已经考虑了 Agent 操作业务系统时的基本安全要求。

但一期安全机制主要解决的是：

```text
一个受控客户端是否能在限定范围内安全调用工具
```

还没有完整解决：

```text
企业中的不同人员能否被可靠识别、授权、审计和追责
```

### 2.6 验收质量评价

仓库给出的验收结果为：

```text
15 个任务 × 连续两轮
30 / 30 通过
26 个 Tool 全覆盖
失败路径覆盖 5 类
```

项目还提供了 Tool 契约、权限矩阵、允许清单、幂等研究、测试任务包、集成验收报告和符合性材料。

相比只提供代码而没有验收依据的普通 MCP 项目，该项目在契约和验证方面明显更完整。

本地复核中还确认了：

1. ERPNext v15 可以运行。
2. MCP Server 可以完成初始化握手。
3. 26 个 Tool 可以正常列出。
4. ERPNext Token 认证有效。
5. MCP 可以执行真实库存查询。
6. 写能力前置检查可以通过。
7. 服务端自检主体逻辑通过。
8. 自检中与作者 Windows 验收目录相关的隔离检查不具备跨平台通用性。

需要保持的客观边界是：

> 当前验收能够证明固定版本、固定站点、固定权限和固定任务集下的功能正确性，但不能直接证明多用户、高并发、长时间运行、灾难恢复和生产安全能力。

### 2.7 工程交付评价

一期最明显的不足不是业务逻辑，而是交付工程化：

1. README 中存在作者本机 Windows 绝对路径。
2. ERPNext 初始化依赖作者既有数据库和主数据。
3. 公司、币种和价格表配置写在源码中。
4. 官方 Docker 子模块默认版本与项目目标版本可能不一致。
5. 缺少一键创建站点、公司、仓库、角色和服务账号的可靠脚本。
6. 端口配置没有完整环境变量化。
7. 权限初始化在不同 ERPNext 版本上的方式不够稳定。
8. 文档存在 16 个 Tool 和实际 26 个 Tool 不一致的问题。
9. 部分自检绑定作者验收目录。
10. 公开文档中出现过开发环境凭据。
11. 项目缺少明确的开源许可证。
12. 缺少正式的发布版本、镜像和升级说明。

这些问题不否定一期核心功能，但会显著增加其他团队复用和部署的成本。

## 3. 一期综合评价

| 维度 | 评价 | 说明 |
|---|---|---|
| 技术路线 | 良好 | 旁挂式 MCP Server 适合 ERPNext 改造 |
| 业务范围 | 良好 | 覆盖进销存最小闭环 |
| Tool 契约 | 良好 | 名称、参数、边界和状态流较清晰 |
| 安全机制 | 中上 | 有白名单、权限、确认和幂等，但缺企业身份与审计 |
| 测试验收 | 良好 | 有契约、任务集和真实后端验收 |
| 部署复现 | 一般 | 依赖作者环境，初始化不够自动化 |
| 可维护性 | 中等 | 模块清晰，但配置与文档存在历史痕迹 |
| 企业生产能力 | 不足 | 缺少身份、审计、HTTPS、运维和高可用 |
| 一期目标完成度 | 基本达成 | 可作为二期基线和受控试用版本 |

总体评价：

> 一期在有限范围内完成了一个可运行、可验证、具有安全边界的 ERPNext MCP 进销存闭环。项目的 Tool 契约和业务状态设计具有实际价值，能够作为二期扩域的基础。其主要不足集中在部署、身份、审计和企业治理，而不是 MCP Tool 本身失效。

## 4. 风险矩阵

### 4.1 风险分级定义

| 级别 | 定义 |
|---|---|
| P0 | 阻断生产上线或可能造成严重数据、安全、财务后果 |
| P1 | 不立即阻断受控试用，但会影响稳定性、可维护性或业务完整性 |
| P2 | 体验、效率、文档或长期演进问题，可在后续持续优化 |

### 4.2 一期已知限制

#### P0 风险

| 风险 | 影响 | 二期处理 |
|---|---|---|
| 真实终端用户身份缺失 | 多个用户通过同一服务账号操作，ERPNext 只能看到 `mcp-service`，无法准确追责 | 增加用户认证、身份映射和调用主体透传 |
| 缺少持久化审计 | 服务重启后会话和批次信息丢失，无法完整证明谁确认并执行了什么操作 | 建立独立审计存储和不可变审计 ID |
| HTTP Token 传输 | Token 可能被网络监听或代理日志泄露 | 强制 HTTPS、证书校验和内网访问控制 |
| 凭据治理不足 | API Secret 主要通过环境变量管理，缺少轮换、吊销和集中托管 | 接入 Secret Manager，建立轮换和失效流程 |
| MCP 确认被误当作企业审批 | 高风险业务可能绕过正式审批流程 | 接入 ERPNext Workflow，区分确认与审批 |
| 共享服务账号权限过大 | Token 泄露后可在角色权限范围内操作多个业务对象 | 缩小权限、按环境或用户拆分凭据并限制来源网络 |

这些风险不阻断本地 PoC，但阻断直接生产上线。

#### P1 风险

| 风险 | 影响 | 二期处理 |
|---|---|---|
| 公司、币种和价格表硬编码 | 无法方便支持多公司和不同部署环境 | 全部配置环境变量化或站点配置化 |
| 批次台账保存在内存 | 重启丢失，不能支持多实例 | 迁移到数据库或 Redis |
| 幂等窗口只在进程内生效 | 重启或多实例可能重复创建单据 | 使用持久化幂等表和唯一业务键 |
| 缺少跨 Tool 事务 | 多步业务链中途失败后需要人工判断和回滚 | 增加业务编排状态、补偿策略和恢复任务 |
| ERPNext 版本绑定 | v15 可用不代表 v16 或定制版本可用 | 建立兼容矩阵和自动回归 |
| 部署过程依赖人工 | 环境容易因端口、版本和基础数据差异失败 | 提供标准 Compose、初始化脚本和部署检查 |
| 聚合查询不足 | Agent 需要多次分页查询并自行计算，容易漏数据或口径不一致 | 建立确定性的经营分析 Tool |
| 多用户并发验证不足 | 高并发下可能产生版本冲突、重复提交或库存竞争 | 增加并发测试和冲突处理策略 |

#### P2 风险

| 风险 | 影响 | 二期处理 |
|---|---|---|
| 文档与代码版本不一致 | 使用者可能误判 Tool 数量和能力 | 由代码生成 Tool 文档 |
| 自检绑定作者目录 | 其他平台运行时出现非业务失败 | 移除绝对路径并参数化测试目录 |
| README 偏验收环境 | 新团队难以快速部署 | 重写安装、运维和故障排查入口 |
| 缺少正式发布包 | 难以追踪升级和回滚 | 建立版本、变更日志和镜像发布 |
| 缺少许可证 | 影响企业采用和再分发 | 明确 License 和使用边界 |

### 4.3 二期业务扩域新增风险

#### P0 风险

| 领域 | 新增风险 | 控制要求 |
|---|---|---|
| 财务结算 | 发票、付款和核销直接影响应收应付及财务账 | 正式 Workflow、职责分离、金额阈值和财务审计 |
| 制造管理 | 错误领料、完工和报废会改变库存与成本 | BOM 版本校验、工单状态校验、仓库和数量控制 |
| 退货与逆向 | 重复退货、超量退货或错误关联原单会造成库存反向错误 | 来源单强关联、可退数量校验和幂等控制 |
| 跨域自动编排 | 销售、库存、财务之间部分成功会造成账实不一致 | 业务编排状态机、补偿策略和人工处置队列 |
| Agent 自动提交高风险单据 | 模型误判可能直接产生财务或库存后果 | 高风险 Tool 默认只读或草稿，审批后才能提交 |

#### P1 风险

| 领域 | 新增风险 | 控制要求 |
|---|---|---|
| 经营分析 | 指标口径不一致导致错误经营判断 | 指标字典、服务端计算和数据时点声明 |
| 财务结算 | 多币种、税费、汇率和舍入规则复杂 | 固定首期支持范围，逐项验证 ERPNext 原生规则 |
| 制造管理 | BOM、多单位、替代料和批次关系复杂 | 分阶段支持，不开放通用自由输入 |
| 退货与逆向 | 批次、序列号和质检状态影响退货路径 | 在 Tool 契约中显式建模 |
| Tool 数量膨胀 | 模型选择错误 Tool 的概率上升 | 按领域分组、优化命名和减少重复接口 |
| 权限矩阵扩大 | 财务和制造 DocType 权限边界更难验证 | 每个领域单独冻结允许清单和权限矩阵 |

#### P2 风险

| 风险 | 影响 | 控制要求 |
|---|---|---|
| Tool 描述过长 | 增加上下文开销 | 提炼描述并把长说明放到资源文档 |
| 不同领域术语冲突 | Agent 可能混淆提交、确认、完成和结算 | 建立统一领域词典 |
| 分析 Tool 输出不统一 | 上层应用难以稳定展示 | 统一分页、时点、单位和金额结构 |

## 5. 二期建设目标

二期采用两条线并行推进：

```text
业务扩域主线
    ├── 退货与逆向
    ├── 经营分析
    ├── 财务结算
    └── 制造管理

生产化辅线
    ├── 配置与部署
    ├── 身份与权限
    ├── 审计与幂等
    ├── 安全与密钥
    ├── 监控与恢复
    └── 兼容与测试
```

资源策略是业务扩域为主、生产化为辅。

但业务优先不代表生产门槛可以跳过。高风险正式写入能力必须满足相应生产化门槛后才允许启用。

建议采用功能开关：

```text
read
plan
draft
submit
cancel
```

不同环境可以逐级启用，而不是新增 Tool 后立即全部开放。

## 6. 二期业务扩域主线

### 6.1 退货与逆向

#### 建设目标

补全一期销售和采购闭环中的逆向流程。

#### 建议能力

| Tool 方向 | 能力 |
|---|---|
| 销售退货计划 | 读取原发货单、可退数量、库存和批次条件 |
| 销售退货草稿 | 按原发货单生成退货 Delivery Note |
| 销售退货提交 | 审批后提交退货并回补库存 |
| 采购退货计划 | 读取原收货单和可退数量 |
| 采购退货草稿 | 按原收货单生成退货 Purchase Receipt |
| 采购退货提交 | 审批后提交退货并扣减库存 |
| 退货状态查询 | 查询原单、退货单和剩余可退数量 |

#### 关键约束

1. 必须关联原始单据。
2. 退货数量不得超过可退数量。
3. 不允许仅通过负数数量模拟任意退货。
4. 批次和序列号必须与原始交易一致。
5. 退货和取消必须是不同 Tool。
6. 重复调用必须有持久化幂等保护。
7. 财务退款不与库存退货隐式绑定，应单独建模。

### 6.2 经营分析

#### 建设目标

把多次基础查询和模型计算改为服务端确定性指标。

#### 建议能力

| 分析领域 | 建议指标 |
|---|---|
| 销售履约 | 未交付订单、逾期订单、履约率、客户未交付金额 |
| 采购履约 | 未收货订单、逾期采购、供应商交付表现 |
| 库存 | 安全库存预警、缺货、积压、呆滞库存、仓库汇总 |
| 周转 | 库存周转天数、近期出入库频率 |
| 异常 | 负库存、价格缺失、重复主数据、异常状态单据 |
| 趋势 | 按日、周、月统计销售、采购和库存变化 |

#### 设计要求

1. 指标由服务端或 ERPNext 报表计算，不让 Agent 自由推导核心数字。
2. 每个指标必须定义时间范围、币种、公司、仓库和数据时点。
3. 金额指标必须声明含税或未税。
4. 分页查询不能直接被当作全量统计。
5. 输出必须同时包含指标值、计算口径和数据截至时间。
6. 分析 Tool 默认只读，适合作为二期最先开放的能力。

### 6.3 财务结算

#### 建设目标

在不开放任意会计分录的前提下，扩展订单后的发票和收付款流程。

#### 首批建议范围

| 能力 | 建议开放级别 |
|---|---|
| 销售发票查询 | 只读 |
| 采购发票查询 | 只读 |
| 应收应付查询 | 只读 |
| 按来源单据生成发票草稿 | 草稿 |
| 收款计划 | 只出方案 |
| 付款计划 | 只出方案 |
| 销售发票提交 | 满足审批门槛后开放 |
| 采购发票提交 | 满足审批门槛后开放 |
| 实际收付款 | 后置开放 |
| Journal Entry | 二期首批不开放通用写入 |

#### 关键约束

1. 发票必须关联订单、发货单或收货单。
2. 税费、币种、汇率和价格不得由模型自由计算。
3. 付款必须校验账户、公司、币种和未结金额。
4. 财务 Tool 必须接入 ERPNext Workflow。
5. 发票和付款提交必须记录真实审批人。
6. 禁止提供通用会计凭证 Tool。
7. 禁止提供任意科目、任意借贷方向输入面。
8. 高金额和跨币种操作应始终要求人工财务审批。

### 6.4 制造管理

#### 建设目标

补充从 BOM 到生产入库的基础制造闭环。

#### 首批建议范围

| 能力 | 建议开放级别 |
|---|---|
| BOM 查询 | 只读 |
| 工单查询 | 只读 |
| 物料需求查询 | 只读 |
| 生产缺料分析 | 只读分析 |
| 工单草稿创建 | 草稿 |
| 领料计划 | 只出方案 |
| 领料单草稿 | 草稿 |
| 完工入库计划 | 只出方案 |
| 完工入库草稿 | 草稿 |
| 工单和库存动作提交 | 满足审批及校验门槛后开放 |

#### 关键约束

1. 工单必须关联有效且已提交的 BOM。
2. BOM 版本和生效状态必须固定。
3. 原材料数量由 ERPNext BOM 计算，不允许模型任意覆盖。
4. 源仓、在制品仓和成品仓必须明确。
5. 超领、替代料、返工和报废必须单独建模。
6. 批次和序列号必须显式处理。
7. 领料、制造和完工入库不能合并成一个不可恢复的 Tool。
8. 二期首批不应支持复杂排产和产能优化自动写入。

## 7. 二期生产化辅线

### 7.1 配置与部署

改造内容：

1. 公司、币种、价格表、站点、端口全部配置化。
2. 提供固定 ERPNext、Frappe、MariaDB、Node 版本矩阵。
3. 提供标准 Docker Compose 或 Helm 部署包。
4. 提供幂等初始化程序。
5. 自动创建角色、服务账号和最小权限。
6. 提供升级、回滚和数据迁移说明。
7. 提供开发、测试、预生产和生产环境模板。
8. 提供健康检查和启动依赖检查。

交付物：

- 标准部署包
- 环境变量模板
- 初始化命令
- 数据迁移脚本
- 运维手册
- 兼容矩阵

### 7.2 身份与权限

改造内容：

1. 建立 MCP 调用用户与 ERPNext 用户的映射。
2. 明确采用用户独立 Token 或服务账号代理模式。
3. 在每次调用中记录真实用户身份。
4. 权限校验同时覆盖 MCP 层和 ERPNext 层。
5. 支持公司、仓库、部门和业务领域隔离。
6. 高风险操作要求职责分离。
7. 不允许所有员工共享同一个高权限 Token。

交付物：

- 身份模型
- 权限矩阵 v2
- 用户映射配置
- 权限回归测试
- 越权测试集

### 7.3 审计与持久化

改造内容：

1. 将批次台账迁移到持久化存储。
2. 将幂等记录迁移到数据库或 Redis。
3. 为每次 Tool 调用生成全局审计 ID。
4. 记录请求人、Tool、参数摘要、确认、审批和执行结果。
5. 记录 ERPNext 单据编号和前后状态。
6. 对敏感字段和凭据进行脱敏。
7. 提供审计查询和导出能力。
8. 定义审计数据保留周期。

交付物：

- 审计数据模型
- 幂等数据模型
- 审计查询 Tool 或管理接口
- 审计保留策略
- 敏感信息脱敏规范

### 7.4 网络与密钥安全

改造内容：

1. 支持 HTTPS。
2. 校验证书，禁止生产环境降级到明文 HTTP。
3. Token 进入 Secret Manager，不进入源码、配置文件或日志。
4. 支持 Token 轮换和吊销。
5. 限制 MCP Server 到 ERPNext 的网络来源。
6. 增加限流、请求大小和超时配置。
7. 增加日志敏感字段扫描。
8. 清理仓库历史中的开发凭据。

交付物：

- HTTPS 接入
- Secret Manager 集成
- Token 轮换流程
- 网络访问策略
- 安全扫描规则

### 7.5 稳定性与恢复

改造内容：

1. 建立超时、重试和熔断策略。
2. 只读请求可受控重试，写请求不得盲目自动重试。
3. 建立多步业务的执行状态机。
4. 为可补偿动作定义补偿策略。
5. 为不可自动补偿动作建立人工处置队列。
6. 定期执行数据库和站点文件备份。
7. 验证备份恢复时间和数据一致性。
8. 设计多实例部署时的共享状态。
9. 增加并发和长时间运行测试。

交付物：

- 恢复与补偿矩阵
- 备份恢复手册
- 灾难恢复演练记录
- 并发测试报告
- 稳定性测试报告

### 7.6 可观测性

改造内容：

1. 采集调用量、成功率、错误率和延迟。
2. 区分 Tool 错误、权限错误、业务校验和后端故障。
3. 监控 ERPNext API、数据库、Redis 和 MCP Server。
4. 为持续失败和异常写入建立告警。
5. 通过审计 ID 关联 MCP 日志和 ERPNext 单据。
6. 提供只包含元数据的安全日志，不记录完整 Token 和敏感业务数据。

交付物：

- 指标体系
- 日志规范
- 告警规则
- 运维仪表盘
- 故障排查手册

## 8. 二期里程碑计划

本计划不在缺少团队规模和上线期限的情况下虚构具体周数，按交付物和准入门槛划分里程碑。

### M1：架构与契约冻结

#### 目标

完成四个新业务域和生产化能力的设计冻结。

#### 主要工作

1. 冻结退货、分析、财务、制造对象范围。
2. 冻结 Tool 命名和参数规范。
3. 冻结权限矩阵和允许清单。
4. 冻结真实用户身份模型。
5. 冻结审计、幂等和批次数据模型。
6. 建立 ERPNext v15 版本基线和兼容策略。
7. 建立风险操作分级。

#### 交付物

- Tool Contract v2
- Object Scope v2
- Permission Matrix v2
- Identity Design
- Audit Design
- Risk Classification
- Acceptance Plan v2

#### 准出条件

1. 每个 Tool 有明确目标对象、前置条件、后置条件和错误语义。
2. 所有正式写操作都有确认、审批和审计策略。
3. 不存在任意 DocType、任意字段或任意 API 输入面。

### M2：低风险业务能力交付

#### 目标

优先交付可快速验证价值且风险较低的能力。

#### 主要工作

1. 经营分析只读 Tool。
2. 退货资格和可退数量查询。
3. 财务应收应付和发票只读查询。
4. BOM、工单和缺料只读查询。
5. 新 Tool 的权限和白名单实现。
6. 配置环境变量化。
7. 标准部署和初始化脚本。

#### 准出条件

1. 只读数据与 ERPNext 原生报表口径一致。
2. 聚合指标不依赖 Agent 自行分页计算。
3. 查询结果包含数据时点和计算口径。
4. 新环境能够通过标准命令完成部署。

### M3：草稿写入能力交付

#### 目标

开放不会立即产生正式业务后果的写操作。

#### 主要工作

1. 销售退货草稿。
2. 采购退货草稿。
3. 销售发票草稿。
4. 采购发票草稿。
5. 工单草稿。
6. 领料和完工入库草稿。
7. 持久化幂等。
8. 持久化审计。
9. 多步执行状态记录。

#### 准出条件

1. 所有写入均可关联真实用户。
2. 所有写入均有审计 ID。
3. 重启和多实例情况下幂等仍然有效。
4. 草稿创建失败不会留下不可识别的半成品。
5. 越权、超量和并发冲突测试全部通过。

### M4：审批与正式生效能力交付

#### 目标

在满足治理门槛后开放高风险状态流转。

#### 主要工作

1. 接入 ERPNext Workflow。
2. 开放退货提交。
3. 开放发票提交。
4. 评估并有限开放收付款。
5. 开放制造领料和完工提交。
6. 建立金额、数量和角色阈值。
7. 建立人工异常处置队列。
8. 完成 HTTPS 和密钥管理。

#### 准出条件

1. MCP 确认和 ERPNext 审批能够被分别审计。
2. 未审批单据不能通过 MCP 提交。
3. 真实操作者可追溯。
4. 高金额和高风险操作有明确审批人。
5. HTTPS、密钥轮换和网络控制已经启用。
6. 回滚和补偿流程经过演练。

### M5：试运行与生产验收

#### 目标

在真实业务环境中进行受控试运行。

#### 主要工作

1. 选择限定公司、仓库和用户组。
2. 先开放查询和草稿，再逐步开放提交。
3. 对照人工流程核验业务终态。
4. 执行并发、稳定性和恢复测试。
5. 执行 ERPNext 升级兼容测试。
6. 完成备份和灾难恢复演练。
7. 汇总试运行缺陷并关闭阻断项。

#### 准出条件

1. P0 风险全部关闭或有正式豁免。
2. 真实业务试运行无账实不一致。
3. 审计日志能够完整还原操作链路。
4. 备份可以恢复。
5. 权限测试无越权。
6. 监控和告警能够发现关键故障。
7. 业务部门和技术团队共同签署验收结论。

## 9. 二期验收标准

### 9.1 功能验收

1. 每个 Tool 的正常路径和失败路径均有测试。
2. 四个业务域分别具备端到端任务集。
3. 退货必须验证可退数量和库存终态。
4. 财务必须验证应收应付、发票和付款终态。
5. 制造必须验证原料、在制品和成品库存终态。
6. 经营指标必须与 ERPNext 原生报表对账。

### 9.2 权限验收

1. 不同角色看到的数据范围符合权限矩阵。
2. 不同公司和仓库之间不可越权。
3. 清单外对象不可访问。
4. 只读角色不能创建草稿。
5. 草稿角色不能提交正式单据。
6. 高风险操作必须由授权审批人完成。

### 9.3 安全验收

1. 生产流量全部使用 HTTPS。
2. Token 不进入代码、日志和普通配置文件。
3. Token 可以轮换和吊销。
4. 接口具备限流和请求大小限制。
5. 敏感数据经过脱敏。
6. 通过基础依赖和凭据扫描。

### 9.4 审计验收

1. 每次调用有唯一审计 ID。
2. 能追溯真实用户、Tool、单据和结果。
3. 能查询确认与审批记录。
4. 服务重启后审计信息不丢失。
5. 审计记录不能由普通业务用户修改。
6. 能从 ERPNext 单据反查 MCP 调用。

### 9.5 并发验收

1. 同参数重复创建不会重复落单。
2. 多实例情况下幂等仍然成立。
3. 陈旧 `modified` 必须产生并发冲突。
4. 库存竞争场景不能静默超发或超领。
5. 并发提交不能产生重复库存或财务流水。

### 9.6 恢复验收

1. 数据库和站点文件均有备份。
2. 能恢复到指定快照。
3. 多步流程失败后能够识别已完成步骤。
4. 可补偿操作能够执行补偿。
5. 不可自动补偿操作进入人工处置队列。
6. 恢复后审计与业务数据保持关联。

### 9.7 兼容性验收

1. 明确支持的 ERPNext 和 Frappe 版本。
2. 每个支持版本执行完整契约回归。
3. 定制 ERPNext App 必须经过兼容测试。
4. 升级前后 Tool Schema 和业务终态保持兼容。
5. 破坏性变更必须有版本号和迁移说明。

### 9.8 试运行验收

1. 在限定用户和业务范围内连续运行。
2. 查询结果与人工核验一致。
3. 草稿单据可由业务人员正常接管。
4. 正式提交链路无未审先提。
5. 无无法追溯的业务写入。
6. 所有 P0 缺陷关闭后才允许扩大范围。

## 10. 保留、重构与暂缓建议

### 10.1 建议直接保留

1. 旁挂式 MCP Server 架构。
2. Tool 注册表机制。
3. 白名单层。
4. 草稿、提交和取消分离。
5. 统一错误模型。
6. 写前校验和写后回读。
7. 乐观并发令牌。
8. 人工确认的失败关闭策略。
9. Tool 契约和任务集驱动的验收方式。

### 10.2 建议重点重构

1. 固定业务配置。
2. 进程内批次台账。
3. 进程内幂等记录。
4. 单一共享服务账号身份模型。
5. HTTP 后端客户端。
6. 权限初始化方式。
7. 环境部署方式。
8. 聚合查询机制。
9. 多步业务编排和失败补偿。
10. 文档与代码同步机制。

### 10.3 建议暂缓开放

1. 通用 Journal Entry 写入。
2. 任意科目借贷操作。
3. 无来源单据的发票写入。
4. 无原单关联的退货。
5. 自动实际付款。
6. 无 Workflow 的财务提交。
7. 自动超领、替代料和报废处理。
8. 通用生产排程自动写入。
9. Agent 自由选择公司、币种、税费和会计科目。
10. 未完成身份和审计建设前的正式生产提交。

## 11. 最终建议

一期项目可以作为二期继续建设的基础，不建议推倒重来。

二期应继续沿用一期的核心原则：

