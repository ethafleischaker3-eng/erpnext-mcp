# ERPNext MCP 二期推进思路框架

> 本文是 [erpnext-mcp-evaluation.md](./erpnext-mcp-evaluation.md) 的落地执行层，面向单人 + AI 的推进方式。
> 定位：把一期验证过的模式变成流水线，用依赖顺序排关键路径，让 AI 扛编码、人守领域正确性。

## 0. 两个前提判断

1. **工程总量**：二期约为一期的 2~3 倍（四域扩域 + 六条生产化辅线）。
2. **AI 提效的真实边界**：AI 能把"样板编码"压缩约一半，把总量差距压到约 1.5~1.8 倍，但压不掉领域正确性这条硬线。（1.5~1.8 倍为量级估算，口径以 §3 的 40~50% 样板占比为准，第一周换实测，见 §3。）

因此，效率瓶颈不是"写代码慢"，而是：

```
写 → 对着真 ERPNext 验 → 发现业务规则 bug → 改 → 再验
```

优化效率 = 缩短这个循环，而不是让 AI 更快地吐代码。

**核心纠正：领域正确性贯穿全链路，不会因分工而消失。** 写一个能挑出"多币种舍入 bug"的验证 fixture，本身就需要先掌握舍入规则——领域正确性没有被压掉，只是从"写实现"挪到了"写验证"，成本没有消失，只是换了位置。

但换位置之后还能再坍缩一次：把 ERPNext 沙箱当 oracle，一次性捕获正确终态存成 fixture，之后每次验证自动断言（见 §5）。规则一旦进 fixture，后续迭代的验证成本接近零。这才是验证层唯一能把领域正确性成本真正摊薄的地方。

## 1. 框架总览（五个层次）

```
① 底座层   —— 规范固化 + 契约单一事实源 + 配置持久化 + 身份模型设计冻结（杠杆，先建）
② 流水线层 —— 契约→代码→测试→文档 自动生成样板          （放大，但只省样板）
③ 推进层   —— 按依赖排的关键路径 + 冻结范围 + 功能开关      （顺序 + 边界，别跳）
④ 验证层   —— ERPNext 沙箱做 oracle，fixtures + 回归为骨干（硬线落点 + 最大杠杆）
⑤ 决策层   —— 参数进 config，可审计理由同版本化，纯思路进 memory
```

## 2. ① 底座层：先做杠杆，不做业务

第一周只干四件杠杆活——三件纯机械、AI 效率最高，一件需人做设计决策；都永不白费：

1. **把一期规范固化成文件** —— `create/confirm/cancel`、白名单、写前校验/写后回读、幂等、错误统一转换，全写进 `CLAUDE.md` + `tool-scaffold` skill。
2. **契约单一事实源** —— 一个 Tool 契约文件，代码 / 测试 / 文档 / 权限矩阵全从它生成，根治"16 vs 26"这类漂移。
3. **配置环境变量化 + 内存态迁持久化** —— 公司 / 币种 / 价格表 / 端口抽出来；批次台账、幂等记录落到数据库。
4. **身份模型设计冻结（P0 #1）** —— 明确"用户独立 Token vs 服务账号代理 vs OIDC"的选型，以及它对权限矩阵、审计、每个写 Tool 形状的级联影响。**设计在 A 冻结，实现才在 C**，不能拖到 C 才想。

   **身份契约作 seam**：把身份契约（调用主体、审计 ID 线程、公司/仓库 scoping 的接口形状）定义成 A 的一个 seam，让 B 的只读 Tool 从第一天就往审计 ID 里吐数据、按 scoping 过滤——即使真正的身份后端 C 才落地。只读 Tool 也要带"谁在查"的痕迹，否则 C 阶段审计链从只读部分就断了。

> 为什么先做这四件：它们是后面每一个 Tool 的共同前置。地基没铺平就写业务，每写一个 Tool 都要重新解释规范、重新处理硬编码，是在重复造轮子。

## 3. ② 流水线层：让"写样板"变便宜，但别夸大

底座建好后，一个新业务动作的产出路径：

```
一句话描述业务动作
   → tool-scaffold skill
   → 自动产出：契约骨架 + 实现骨架 + 测试骨架 + 文档 + 权限矩阵条目
   → 一条命令回归验证
```

**诚实校准**：scaffold 只省**样板**（契约骨架、权限矩阵条目、文档、测试骨架），约占一个 Tool 的 40~50%。超领校验、可退数量、BOM 版本固定这些**领域逻辑必须手写 + 验**，剩下那一半不压缩。本项目因 `create/confirm/cancel` 模式高度统一，样板占比会高于通用值，但仍不是"趋近于零"——按约一半排资源，不按"免费"排。

**40~50% 目前是估算，第一周就换成实测**：建完 scaffold skill 后，拿第一个真实 Tool 做一次前后计时（手写样板 vs skill 产出），把 40~50% 换成实测值。这样 §0 的"总量 1.5~1.8 倍"和 §7 的资源表就从估算变成基线，后面 30 个 Tool 都拿它做参考。

## 4. ③ 推进层：依赖排关键路径 + 冻结范围 + 功能开关

### 关键路径

```
A 底座改造  →  B 只读扩域  →  C 草稿写入  →  D 审批+正式提交  →  E 受控试运行
   ↓              ↓              ↓               ↓
 配置/持久化    分析/退货/财务   身份+审计先补      Workflow+HTTPS
 身份设计冻结   制造只读查询     再做草稿Tool      +密钥+并发测试
```

### 依赖逻辑

正式提交（D）的准入门槛 = 身份 + 审计 + HTTPS + Workflow 全就位，这些正是最慢的活，所以必须拆成前置、逐步解锁，而不是一上来就做财务提交然后被卡死。

### 各阶段要点

| 阶段 | 内容 | 关键纪律 |
|---|---|---|
| A 底座改造 | 配置化、持久化、标准部署、文档生成化、身份模型设计冻结 | 幂等化必须逐项验证，别只信 AI |
| B 只读扩域 | 经营分析、退货资格、财务应收应付/发票、BOM/工单/缺料只读 | 零**写入**风险，非零正确性风险；先交付，指标与 ERPNext 报表对账 |
| C 草稿写入 | 先实现身份映射 + 持久化审计，再做退货/发票/工单草稿 | 每个写入关联真实用户 + 有审计 ID，失败不留半成品 |
| D 审批+正式提交 | Workflow 接入、退货/发票/制造提交、HTTPS/密钥/越权并发测试 | 上线门槛清单在这一步一起验收 |
| E 受控试运行 | 限定公司/仓库/用户组，先查询草稿再逐步开提交 | P0 全关闭才扩大范围 |

### 冻结范围（scope 是比 throughput 更大的风险）

流水线让"加 Tool 变便宜"的同时会鼓励加 Tool。30+ Tool 对单人仍是 scope 陷阱。**在 B 阶段冻结一张"二期只做这些、其余进暂缓清单"的清单**，直接承接原文档 §10.3，别让"边际成本减半"变成"边际范围无限"。

### 功能开关（承接原文档 §5）

显式承接 read / plan / draft / submit / cancel 逐级启用：新增 Tool 不立即全部开放，按环境逐级解锁。这是最有价值的风险控制机制之一，作为跨阶段常量。

### 串行不等于一切排队

关键路径串行是保专注、防返工的，但**纯 AI 机械活（配置持久化、幂等持久化等"AI 写、人只验幂等"的任务）可在 B 的只读对账空档并行跑**，不必死等 A 全部收尾。串行约束的是"需要人注意力/决策的活"，不是"AI 能独立推进的活"。

### 阶段 D 上线门槛清单（原文档 §11）

真实用户身份、持久化审计、持久化幂等、HTTPS、密钥治理、ERPNext Workflow、并发验证、备份恢复、异常补偿。

## 5. ④ 验证层：ERPNext 沙箱做 oracle，golden fixtures + 回归为骨干

验证是领域正确性的最终落点，不是它的避风港——成本没有消失，只是从"写实现"换到了"写验证"。但成本换位置之后还能再坍缩一次，这正是验证层最大的杠杆：

### 真值从哪来：ERPNext 沙箱当 oracle

golden fixture 的正确值不由人凭空编写，而是**用一个可重复播种的沙箱 ERPNext 实例当 oracle**：

```
在沙箱里跑一遍真实动作
   → 捕获跑出来的终态（库存流水、应收应付、舍入后的金额、单据编号）
   → 存成 golden fixture
   → 之后 MCP Tool 的测试断言"复现出同样的终态"
```

这样"对着真机验"就从"每次人手动盯"变成"一次性捕获、之后每次脚本自动断言"。规则一旦进 fixture，后续迭代的验证成本接近零——这是验证层唯一能把领域正确性成本真正摊薄的地方，也是人力 ROI 最高的一项。前提是一期已有可运行 ERPNext v15，沙箱成本可控。

- **骨干（最高 ROI，确定、便宜、可复用）**：
  - **ERPNext 沙箱 oracle**：真值来源，见上。
  - **golden fixtures**：从沙箱捕获的可重复播种基础数据 + 终态断言。
  - **回归脚本**：一期 30/30 变成一条命令，1 分钟知道有没有破坏业务规则。
- **红蓝对抗（降级为后期可选 stress test，非骨干）**：噪声高、确定性低，只在 golden fixtures 已建好、需要向外探索盲区的高风险域（财务舍入、制造库存、退货超量）上按需启用，不作为通用层。

### 核心度量

整个框架的命题是"缩短 write→verify 循环"，必须可验证。**先基线，后目标**——第一周先各测一次"发现业务规则 bug → 回归通过"的耗时和逃逸率作为基线，再定目标值，否则"缩短循环"还是口号。两个指标：

1. **循环速度**：发现业务规则 bug → 回归通过 的耗时（以及每个 Tool 的平均回归轮次）。
2. **逃逸率**：漏到真机验证才发现的 bug ÷ 应被 golden fixture / 回归提前抓住的 bug。

逃逸率分母要可操作，避免变成虚荣指标：一个 bug **只有在"找到后能廉价补一条 fixture 抓住它"时才计入分母**；补不进 fixture 的说明是真实覆盖缺口，单独记录，不混入逃逸率。逃逸率比耗时更接近本框架的命门——它直接度量"验证层到底有没有真值"。

## 6. ⑤ 决策层：可执行参数与决策理由分层

治理决策分三类，别混：

| 类型 | 例子 | 存哪里 |
|---|---|---|
| **可执行参数** | 金额阈值、开放级别、审批层级、职责分离 | 进 ① 的 contract / config，被机器强制，可审计、可版本化 |
| **可审计的决策理由** | "为什么财务门槛定 10 万"（需要回答"为什么拦了这笔 12 万的单"） | 与 config 值**同版本化**（config 旁注释 / ADR），不能散在 memory |
| **纯思路理由** | "为什么先做退货后做制造、而不是反过来"（推进顺序取舍） | 进 memory，被引用，不可靠召回也不影响正确性 |

错误示范：把阈值"记在 memory 里、但代码里没实现"——这正是原文档反复警告的"16 vs 26 漂移"的翻版。**memory 不是决策账本，config 才是。**

## 7. 资源分配原则

| 层级 | 谁干 | 该阶段人的投入强度（注意力权重） |
|---|---|---|
| 底座 / 流水线 | AI 批量写 | 10%（只验幂等和初始化真实跑通） |
| 只读扩域 | AI 写 | 20%（只盯对账） |
| 草稿写入 | AI 写，人定身份模型 | 30% |
| 审批 + 正式提交 | 人主导，AI 辅助 | 60%（业务规则真机验证） |
| **验证层** | **人亲自上手**，AI 只生成 fixture 骨架和跑回归 | **最高单项（60%+）——fixture 编写与真值确认是人最该亲自做的地方** |

> 表内数字指各阶段**人的注意力权重**，非时间百分比，不可加总。

**趋势：业务阶段越往后，AI 占比越低、人的占比越高——但验证层是横跨全程、且注意力最高的单项，不随阶段递减。** 领域正确性这条硬线贯穿全链路，验证只是它的最终落点，不是唯一消耗点。

## 8. 与原评估文档 M1-M5 的映射

| 本框架阶段 | 原文档里程碑 | 关系 |
|---|---|---|
| A 底座改造（含身份设计冻结） | M1 架构与契约冻结 + 部分 M2 | 契约冻结落地为规范固化 + 单一事实源；**身份模型设计冻结归 A，不再丢** |
| B 只读扩域 + 范围冻结 | M2 低风险能力交付 | 一致，并新增 scope 冻结 |
| C 草稿写入 | M3 草稿写入能力交付 | 一致，身份实现前置 |
| D 审批 + 正式提交 | M4 审批与正式生效能力交付 | 一致 |
| E 受控试运行 | M5 试运行与生产验收 | 一致 |

差异点：把"两条线并行"改为"单关键路径 + AI 机械活空档并行"，把"业务优先、生产化为辅"细化为"按依赖逐级解锁"，并补回身份设计冻结、范围冻结、功能开关、度量四项。

## 9. 一句话总结

> 先用底座和流水线把"写样板"变成便宜的模板活（约省一半，不是免费），再用依赖顺序 + 范围冻结把 30+ 个 Tool 和治理门槛排成一条不返工的关键路径，把可执行参数落进 config、可审计的决策理由与参数同版本化、纯思路留在 memory，最后把领域正确性——无论实现还是验证——都按真实成本预算。

## 10. 落地第一步

从 **① 底座层的规范固化** 开始：读一期代码，把 `create/confirm/cancel` 这套规范提炼成 `CLAUDE.md` + `tool-scaffold` skill；同阶段并行推进身份模型设计冻结（P0 #1）。
