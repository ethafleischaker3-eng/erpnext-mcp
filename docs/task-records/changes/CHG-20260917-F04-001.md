## 缺陷与证据

1. F02 realsmoke 以真实 MCP server + 真实客户端（auto-accept）跑销售/采购写链路时，#13（全自动，无确认）通过，**#14（人确认，走 server 侧 elicitation）挂起不返回**。
2. 根因：`server/index.js` `handleMessage` 的 default 分支路由 `elicitation/create` 应答时，读取 `params.result.action`；但客户端按标准 JSON-RPC 回 `{ jsonrpc, id, result: { action: 'accept' } }`，`action` 在 `result.action`，不存在 `params` 字段，导致条件恒假、`pendingElicitations` 的 resolve 永不触发 → 人确认 tool 永久挂起。
3. 影响：**全部 14 个人确认 tool**（#6–#12、#14/#15/#17/#18/#20/#22/#24）经真实 server 调用均会挂起；F04 首次验收时未覆盖「真实 MCP server + 客户端确认应答」全链路，故未暴露。

## 变更内容（前后对照）

- 变更前：
  ```javascript
  if (pendingElicitations.has(id) && params && params.result) {
    const action = params.result.action || 'cancel';
  ```
- 变更后：
  ```javascript
  if (pendingElicitations.has(id) && msg && msg.result) {
    const action = msg.result.action || 'cancel';
  ```

## 影响分析

- 是否重新实施：否（仅修正应答路由的读取字段，不改协议、不改确认语义、不改 fail-closed 口径）。
- 是否重新验收：F02 realsmoke 复测 #14/#15/#17/#18/#20/#22 确认链路即可覆盖；F04 人确认 tool 的既有 mock 自检不受影响。
- 受影响任务包：F04（底座缺陷）；F02（下游，解锁人确认 tool 真实后端实测）；G01（集成验收）。
- 安全影响：无权限面变化；仅修正「accept/decline/cancel 应答能否被 server 收到」，`decline`/`cancel`/客户端不支持时的零副作用与 fail-closed 语义不变。

## 评审结论

**已批准（gjg/Owner，2026-09-17）**。修正 `server/index.js` elicitation 应答路由，读取 `msg.result.action` 而非 `params.result.action`。后续：F02 以 `server/test/realsmoke.js` 复测 #14–#22 人确认链路（auto-accept），确认不再挂起并落库/转译正确。
