## 2. 目标

在不开发任何正式业务 tool、不接入 ERPNext 后端的前提下，用隔离的最小确认能力探针，对目标客户端是否支持 server 侧发起的确认机制进行实测，产出可复核的验证记录并冻结结论，作为项目 L3/L2 形态及后续 B01～B05、E05 与正式业务 tool 开发的权威输入。验证记录必须逐项覆盖：

1. **目标客户端与传输方式**：客户端名称 + 版本 + 传输方式（stdio / HTTP / SSE 等）；优先评估 Claude Agent SDK 官方规范作为客户端承载/嵌入层（SDK 自动打包平台适用 CLI 二进制，屏蔽底层传输差异，保证确认能力可比性），但必须同时核查该承载层将 server 侧确认请求呈现给最终用户（人确认）的**确认面**及应答回传路径，而非仅核查 SDK 是否声明支持；
2. **MCP 协议版本与确认机制语义**：接入时实际使用的 MCP 协议版本，及该版本下 server 侧发起确认（elicitation / `elicitation/create`）的能力与消息语义；探针在初始化握手阶段读取并校验协议版本号后再加载对应处理逻辑，不硬编码字段名/交互模式；协议版本「动态适配层（Adapter）」作为未来正式 MCP server 的架构决策（记入 D01/E05 下游输入），不纳入本包一次性探针；
3. **确认请求是否由 server 侧发起并呈现给用户**：确认动作由 server 发起（而非依赖客户端权限配置），且客户端确实向用户呈现了确认请求；
4. **完整参数展示**：确认请求展示完整 tool 调用参数（tool 名 + 全部参数 + 拟执行动作），不得只给 tool 名称或摘要；
5. **用户拒绝/取消时 fail-closed**：用户拒绝或取消时，server 必须返回可自纠错误且不发生任何业务副作用，不得静默写入或降级为直接执行；
6. **客户端不支持时 fail-closed**：客户端不支持 server 侧确认机制时，server 必须拒绝执行并返回可自纠错误，不得降级为直接执行；
7. **敏感凭据 form / URL 模式**：server 不得用表单（form）模式索取密码、密钥等敏感凭据，必须走跳转（URL）模式；核查目标客户端对两种模式的支持与行为；
8. **确认请求的发起时机**：server 发起的确认请求只在处理某个客户端请求期间发出，不得凭空出现；
9. **结论**：核查通过 → L3 成立；不通过 → 所有写操作 tool（含原定全自动草稿创建）均拒绝写入、只能返回 plan，项目降为 L2 受限形态。结论由接入方确认有效。

验证记录为冻结输出，其内容结构见第 9 节，是下游任务的权威输入；探针本身与探针运行结果不构成任何正式业务 tool 或业务 tool 验收依据（总则 §16.1）。

## 9. 输入输出契约

A01 不提供正式业务 tool，不定义业务 tool 语义或 schema。本节规定两件事：(a) 探针 tool 的临时契约；(b) 验证记录的冻结输出结构（下游权威输入）。

### 9.1 探针 tool 临时契约（仅能力核查，非业务 tool）

| 项 | 规定 |
|---|---|
| 探针 server | 隔离 MCP server，位于 `docs/task-packages/A01/probe/`；声明 server 侧确认能力（elicitation）；不接入 ERPNext |
| 探针 tool 名 | `probe_confirm_write`（能力核查用临时命名，不得使用 `erpnext_*` 前缀，不得复用为正式业务 tool） |
| 业务语义 | 模拟「人确认」档写动作：收到调用 → server 发起确认 → 用户应答后才决定是否发生本地副作用 |
| annotation | 显式声明：只读=否、破坏性=是、幂等性按探针实现如实声明、是否与外部世界交互=否（§8.1） |
| 输入 | 合成业务参数（如目标对象标识 + payload），不含任何真实业务数据或真实凭据 |
| 确认请求内容 | 必须含 tool 名、完整参数、拟执行动作；不得只给名称或摘要（§9.7） |
| 确认应答路径 | 确认 → 写本地合成标记并返回成功；拒绝/取消 → 返回可自纠错误且不写标记；客户端不支持 → 返回可自纠错误且不写标记（fail-closed） |

### 9.2 验证记录输出契约（冻结输出，下游权威输入）

验证记录（交付物 D05）必须逐项包含并可复核：

1. 客户端承载/嵌入层名称、精确版本、传输方式（若经 Claude Agent SDK 承载，同时记录 SDK 版本与实际确认面）；
2. 实际 MCP 协议版本及确认机制语义；
3. 确认请求是否由 server 侧发起并经确认面呈现给最终用户（支持/不支持 + 证据引用；证据须落在实际呈现确认请求给用户的承载/嵌入层，而非仅 SDK 能力声明）；
4. 确认请求是否展示完整 tool 调用参数（证据引用）；
5. 用户拒绝/取消时的 fail-closed 结果（副作用未发生 + 可自纠错误，证据引用）；
6. 客户端不支持确认时的 fail-closed 结果（副作用未发生 + 可自纠错误，证据引用）；
7. 敏感凭据 form/URL 模式核查结果（证据引用）；
8. 确认请求发起时机核查结果（证据引用）；
9. **结论**：支持 → L3 成立；不支持 → 所有写操作 tool 只能返回 plan、项目降为 L2 受限形态；
10. 接入方（gjg）确认有效的签署记录。

验证记录一经冻结，写入符合性材料或成为下游权威输入时均须走变更控制；A01 本身不改变 PRD 冻结语义。

## 10. 不变量

- 冻结 PRD、总则、模板、登记表结构与边界规则内容不得被 A01 修改；
- 确认动作必须由 server 侧发起，不得依赖客户端权限配置实现；
- 客户端不支持或用户拒绝时，server 必须 fail-closed（返回可自纠错误 + 零副作用），不得降级为直接执行；
- 确认请求必须展示完整 tool 调用参数，不得只给名称/摘要；
- 敏感凭据绝不走 form 模式，只走 URL 模式；核查只用占位/合成值；
- server 发起的确认请求只在处理客户端请求期间发出；
- 探针不得成为或复用为正式业务 tool；探针结果不得代替业务 tool 验收；
- 核查不通过时结论必须为 L2 受限形态（所有写 tool 只能返回 plan），不得宣称 L3；
- 不接入、不改变 ERPNext 后端或任何数据库状态；
- 凭据值、完整认证头、完整堆栈不得出现在证据、提交或公开实施区；
- 实施会话不得读取验收材料；不得将隐藏验收材料反馈给实施侧。

## 15. 停止与升级条件

继承《MCP 改造任务包总则》第 6.15 节。另有以下 A01 条件时，停止受影响工作并转为「待澄清」：

- 目标客户端无法连接探针，或探针无法可靠启动；
- MCP 协议版本无法确定，导致确认机制语义无法客观判定；
- 探针依赖无法在隔离范围内满足，且无法改用最小 stdio/JSON-RPC 免依赖实现；
- 需要接入 ERPNext 后端、数据库或任何外部服务才能完成核查；
- 需要修改冻结 PRD、总则、模板、登记表结构或边界规则；
- 需要新增对象、tool、权限或外部依赖。

**注意**：「客户端不支持 server 侧确认机制」不是停止条件，而是可判定的有效结论——按 PRD 决议 1 与总则 §16.1，结论为 L2 受限形态，所有写操作 tool 只能返回 plan。只有当无法取得可复核的确定性结论时，才触发停止与升级。
