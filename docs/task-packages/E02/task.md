## 2. 目标

在**不接入 ERPNext 后端、不改变任何数据库状态、不冻结任何业务 tool 契约**的前提下，实现并冻结一套 tool 无关的 MCP server 侧「写操作安全底座」，作为 D02 冻结契约与 F 包业务实现的公共机制，落地三块能力：

1. **幂等机制**：将 B05 §18.3 结论实现为可运行的 server 侧机制——指纹由 server 依业务参数规范化计算且 agent 不感知、传输/客户端字段不进指纹；窗口期 create 组 300s / confirm·cancel 组 60s（不得放宽）；窗口期内同参命中返回首次结果 +「重复请求已按幂等合并」；confirm/cancel 组以状态断言兜底（命中返回幂等成功「已在目标状态」，非通用错误）（B05 §18.3、PRD §5.1、规范 §9.3）。
2. **前置断言与事后校验框架**：落地规范 §9.4/§9.5 的两层拆分——前置断言（schema 层协议已覆盖 vs 业务状态层未覆盖）、事后校验（返回值形状协议已覆盖 vs 写后回读终态未覆盖）；提供业务状态断言与写后回读的**挂钩**，具体逐 tool 断言/回读由 D02 契约与 F 包落地（PRD §5.2/§5.3）。
3. **批次台账与状态查询**：落地 PRD §5.4——一次 `tools/call` 一批次、server 生成批次标识、同批变更、回滚路径（草稿删/生效取消/已取消不可回滚）如实记录；批次 Owner 持久化与查询授权依 B00 §18.3 身份结论冻结；实现 #26 `erpnext_batch_status_get` 的只读查询逻辑（agent 只查自身批次、不可查他人、不可主动回滚，管理员可查全量）。

产出物为可运行的机制实现（server 侧模块/函数）与《实现契约》（本包交付物 CD-5，见第 11 节），其内容结构见第 9 节。D02 冻结各 tool 契约与 F 包接入时，必须引用本包冻结的实现契约，不得另起口径。

## 9. 输入输出契约

E02 不提供业务 tool，不定义业务 tool 语义或 schema。本节规定两件事：(a) 机制实现契约的冻结输出结构（下游 F 包接入依据）；(b) 档位 2 的独立验收口径。

### 9.1 机制实现契约输出结构

《实现契约》（交付物 CD-5）必须逐项包含并可复核：

1. **幂等机制接口**：指纹函数口径（server 依业务参数规范化、agent 不感知、传输/客户端字段不进指纹、同参同指纹异载异指纹）；窗口期常量（create 300s / confirm·cancel 60s）与放宽禁令；命中合并返回口径（「重复请求已按幂等合并」+ 首次结果）；业务引用号的可选接入点与「是否进指纹由 D02 冻结」的边界（B05 §18.3、PRD §5.1、规范 §9.3）；
2. **confirm/cancel 状态断言接口**：状态断言命中 = 幂等成功（「已在目标状态」）的可验收语义；「具体返回结构由 D02 冻结」的边界；不返回通用错误、不误导 agent 的硬约束（B05 §18.4 第 2 条、idempotency-research.md §7.2）；
3. **前置断言框架接口**：两层拆分（schema 层协议已覆盖 / 业务状态层未覆盖）；业务状态断言挂钩的接入点与失败返回口径；「完成 schema 校验不等于满足前置断言」的硬约束（规范 §9.4、PRD §5.2）；
4. **事后校验框架接口**：两层拆分（返回值形状协议已覆盖 / 写后回读终态未覆盖）；写后回读编排、不一致→报错→记批次→标记待回滚的口径；「返回值符合 schema 不等于写入成功」的硬约束（规范 §9.5、PRD §5.3）；
5. **批次台账接口**：批次标识生成、同批变更聚合、回滚路径记录（草稿删/生效取消/已取消不可回滚）、批次依赖顺序（跨批次倒序回滚）；批次 Owner 持久化与查询授权（普通调用方只查自身、管理员查全量）依 B00 §18.3 身份结论（PRD §5.4）；
6. **#26 状态查询语义**：`erpnext_batch_status_get`（#26）的只读可见性边界（归属自身批次可查、他人批次不可见、不可主动回滚）、返回内容（涉及对象、状态、回滚结果）；契约（name/schema/annotation）由 D02 冻结，本包只冻结查询语义与实现（PRD §3.3 #26、§5.4）；
7. **机制的可接入性声明**：每个接口的接入点（hook）、入参/出参形状、错误分类——供 D02 契约与 F 包实现引用，不得在实现契约中写死任何单个业务 tool 的 name/schema/断言。

> 实现契约一经冻结，成为 D02 契约与 F 包接入的权威依据；修改须走变更控制（总则 §12）。E02 本身不改变 PRD 冻结语义，也不替代 D01 公共契约。**内容边界**：D01 冻结「契约口径（做什么）」，E02 只冻结「实现层挂钩/接口（怎么做）」；§9.1 第 3/4/5/6 项与 D01 公共契约重叠时，以 D01 已冻结口径为准，E02 不反向改写。

### 9.2 档位 2 的独立验收口径

E02 为档位 2（标准），需独立验收（客观验证）。验收不依赖正式验收题或隐藏材料，以隔离探针 + 单元测试构成可复算断言：

- **幂等**：同参两次调用（含键序不同）→ 同指纹、第二次命中返回合并结果；异载 → 异指纹不命中；传输/客户端字段注入 → 指纹不变；窗口期命中与超期不命中行为可复算（对应 B05 §7.1/§7.2 两组验收方法的机制层实现）；
- **confirm/cancel 状态断言**：模拟「已在目标状态」→ 返回幂等成功语义，非通用错误（B05 §7.2 的机制层）；
- **前置/事后校验框架**：模拟断言失败/回读不一致 → 返回对应可自纠报错并记批次、标记待回滚（规范 §9.4/§9.5 机制层）；
- **批次台账**：模拟多批次写入 → 批次标识、同批变更、回滚路径、归属可见性边界均可复算；普通调用方不可见他人批次、管理员可查全量（PRD §5.4 机制层）。

完成判定：机制实现覆盖 §9.1 全部 7 项、开发自检通过、Evidence Manifest 完整可复核、且 Acceptor（gjg）独立验收通过。

## 10. 不变量

- 冻结 PRD、规范、总则、模板、登记表结构与边界规则内容不得被 E02 修改；
- 幂等边界与 B05 §18.3 一致：窗口期不得放宽、指纹由 server 规范化且 agent 不感知、传输/客户端字段不进指纹；
- agent 传入的随机 request id 或幂等键不得成为可信覆盖值，不得参与或覆盖 server 生成的幂等指纹（规范 §9.3；PRD §5.1 第 219 行）；
- 有效负载不同不得命中同一指纹；独立的合法重复业务不得被幂等机制合并（总则 §6.10）；
- confirm/cancel 状态断言命中必须返回幂等成功语义，不得以通用错误误导 agent（B05 §7.2）；
- 机制不得绑定具体传输层字段（`id`/`progressToken`/`claudecode/toolUseId` 等，规范 §9.3、B05 结论）；
- 后端不可达时写操作不得自动重试（总则 §6.10）；
- 错误不得以成功响应伪装、失败路径不得静默成功（总则 §6.10 项目级不变量；规范 §8.6/§9.5）；
- 普通调用方不得读取其他调用方的批次信息；管理员可查全量（PRD §5.4；仅以 B00 §18.3 身份结论允许的隔离为准，未确定性冻结前不得宣称隔离成立）；
- 不接入、不改变 ERPNext 后端或任何数据库状态；不读取 C01a 题目正文、隐藏数据或终态断言；
- 未经实测/未经上游冻结结论的表述不得写入实现契约（不得以推测代替结论）。

## 16. 风险、假设与待决事项
