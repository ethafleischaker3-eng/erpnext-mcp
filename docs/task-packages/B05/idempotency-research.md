## 2. `tools/call` 重试行为结论（W04/W05/W06，三层区分）

### 2.1 静态分析（SDK 层，权威）

MCP SDK `dist/esm/shared/protocol.js`（v1.29.0）：

- **无重发循环**：`request()` 一次发送、一次等待；无 retry 逻辑。
- **超时**（默认 `DEFAULT_REQUEST_TIMEOUT_MSEC = 60000`）：超时 → `cancel()` → 发 `notifications/cancelled(requestId, reason)` + 拒绝 `McpError(RequestTimeout)`，**不重发**。
- **断线**：`_onclose()` 对所有未决请求拒绝 `McpError(ConnectionClosed)`，**不重发、不重连**（重连是客户端应用职责，SDK transport 不负责）。
- **请求 `id`**：`this._requestMessageId++` 单调计数器，每请求新值。
- **`_meta.progressToken`**：仅当调用方设 `onprogress` 时附加 `progressToken = messageId`（= id）；非重试关联机制。
- stdio 无 `sessionId`/`resumptionToken`（仅 streamable HTTP 存在）。

### 2.2 动态实测（Claude Code harness/模型层）

| 场景 | 观测 | 结论 |
|---|---|---|
| 基线（同会话两次调用） | 两次 `tools_call`，`id` 递增（2、3），`progressToken` 随 id 递增，无重发 | 每次调用新请求、新 id，无可复用标识 |
| 业务错误（`isError=true`） | 第 1 次 id=2（error），模型改 payload（`p-err`→`p-ok`）重新发起，第 2 次 id=3、新 `toolUseId` | 模型自纠重试 = 新请求，非透明重发 |
| 断线（进程 crash） | 仅 1 次 `tools_call`（id=2），随后 `fault_crash` 进程退出；客户端报 `MCP error -32000: Connection closed`，**未自动重发、未自动重连**，模型仅询问是否重试 | 断线不透明重试；错误上抛给模型/用户 |
| 超时（70s 慢响应） | 单次 `tools_call`，客户端**等待 70s 完整返回**（无 `notifications/cancelled`），未触发 SDK 默认 60s 超时 | Claude Code 覆写/放宽了 60s 超时；慢响应不重发 |

### 2.3 三层重试结论

- **传输/SDK 层**：不自动重试（静态 + 动态一致）。
- **客户端/harness 层**：不透明重试——断线/超时错误上抛给模型，不重发同一请求。
- **模型/agent 层**：可能重新发起 `tools/call`（业务错误场景实测发生了自纠重试），但这是**新请求**（新 `id`、新 `progressToken`、新 `claudecode/toolUseId`、payload 可同可不同），对 server 而言与「合法新业务」不可区分。

## 3. 关联信号判定矩阵（W07）

候选信号逐项判定「server 可观察 / agent 可伪造 / 违反 §9.3·§6.2 / 跨重试可关联」：

| 信号 | 位置 | server 可观察 | agent 可伪造 | §9.3/§6.2 合规 | 跨重试可关联 | 可用于幂等关联 |
|---|---|---|---|---|---|---|
| JSON-RPC `id` | 请求顶层 | ✓ | ✗（SDK 单调计数器） | 协议层字段，非传输层，合规 | ✗（每请求新值） | ✗ |
| `progressToken` | `params._meta` | ✓ | ✗（SDK 设 = id） | 协议层字段，合规 | ✗（每请求新值 = id） | ✗ |
| `claudecode/toolUseId` | `params._meta` | ✓（单次调用/重试轮次出现，多调用同轮次未出现） | ✗（harness 分配 `call_00_*`） | **客户端特定字段**（`claudecode/` 命名空间），绑定特定客户端，违反 §6.2「不依赖特定客户端」精神 | ✗（每 tool_use 新值） | ✗ |
| stdio 进程/连接身份 | 传输层（进程对） | ✓ | ✗ | 传输层特定，绑定 stdio 违反 §9.3 | ✗（会话内所有请求同身份，无法区分重试与新建） | ✗ |
| `sessionId`/`resumptionToken` | — | ✗（stdio 下不存在） | — | 仅 streamable HTTP 有 | — | ✗ |

**判定结论：不存在「既合规可信、又能跨重试关联同一业务意图」的信号。** 可观察且非 agent 伪造的信号（`id`/`progressToken`/`toolUseId`）均为**每请求/每 tool_use 新值**，无法把一次重试关联到其原请求；会话级身份（stdio 进程）对所有请求相同，无法区分「重试」与「合法新建」；且 stdio 下无 `sessionId`/`resumptionToken`。

## 4. 分叉决策（W08）：无可信信号 → 业务层方案

依 §3 结论走 PRD §5.1 第 218 行「不存在」分支，选择业务层方案并记录残余风险：

1. **confirm/cancel 组（#14、#15、#17、#18、#20、#22、#24）**：以**状态断言为主兜底**（confirm 仅草稿、cancel 仅已生效，PRD §5.1/§5.2）。第二次 confirm/cancel 因「已非合法前态」前置断言失败，天然「只变更一次」；窗口期仅用于并发/在途重复提交的去重。合法重复业务在此组不适用（同一单据不能合法 confirm/cancel 两次）。
2. **create 组（主数据 #6、#8、#10；草稿 #13、#16、#19、#21、#23）**：无状态断言兜底，仅凭业务参数无法区分「重试」与「合法同参数重复」。方案：
   - **业务引用号（可选增强，交 D02 择定）**：对存在自然外部标识的对象（如订单的客户采购单号/供应商单号），将业务引用号设为可选业务字段并纳入指纹——同引用号=同意图、不同引用号=合法重复；无自然标识的对象（主数据 create、调拨/收货/发货）不强制，靠窗口期 + 误合并策略。
   - **窗口期缩短**：从 24h 初始假设缩到「模型重试时延」量级（见 §6）。
   - **误合并策略**：窗口期内同参数命中 → 返回首次结果 +「重复请求已按幂等合并」；误合并的残余风险通过 #26 `batch_status_get` 暴露（agent 可查「是否已建过这笔」），由 agent 自行核对后再决定是否补建。

## 5. 幂等指纹不可覆盖结论（W09）

- 指纹 MUST 由 server 依**业务参数**规范化计算（稳定排序 + 归一化），agent 完全不感知（规范 §9.3）。
- agent 传入的随机 request id 或幂等键、以及 JSON-RPC `id`/`progressToken`/`claudecode/toolUseId` 等传输/客户端字段，**一律不参与指纹、不得成为可信覆盖值**（PRD §5.1 第 219 行）。
- 探针实测：相同业务参数（键序不同）→ 同指纹；不同有效负载（`payload` 不同）→ 不同指纹；指纹函数不含任何 JSON-RPC id/连接身份（`evidence/S03-selftest.txt` 25 项自测通过）。

## 6. 窗口期冻结值（W08/W10）

> 24h/1h 为 PRD §5.1 调研初始假设，本结论予以**冻结替代值**，依据为本包实测重试时延。

| 组 | 冻结窗口期 | 依据 |
|---|---|---|
| confirm/cancel（#14、#15、#17、#18、#20、#22、#24） | **60 秒** | 状态断言为主兜底；窗口仅覆盖同一事务的并发重复提交在途时长（秒级），60s 已充裕 |
| create（主数据 #6、#8、#10；草稿 #13、#16、#19、#21、#23） | **300 秒（5 分钟）** | 实测无透明重试、无超时重发；模型自纠重试在秒级（实测约 2.5s）内以新请求发生；5 分钟覆盖同会话模型重试 + 进程重启合理裕量，把误合并暴露面从 24h 缩减 99.65% |

> 说明：窗口期为 B05 冻结的「同一业务意图」判定边界初始值；E02 实现时不得放宽（缩短须走变更）。confirm/cancel 若后端单事务原子提交 + 状态断言已足够强，窗口值可进一步由 D02 确认，但默认按上表。

## 7. 「同一业务意图连续调用只变更一次」的可执行验收方法（W10）

对应规范 §12.3「幂等冲突」失败路径题，对每个写 tool 至少 1 题：

- **题目**：同一业务意图连续调用两次（参数完全相同，或仅展示性备注不同）。
- **断言**（可执行、客观终态）：
  1. 第一次调用成功，返回符合声明的成功契约；
  2. 第二次调用在窗口期内命中指纹，返回「重复请求已按幂等合并」+ 首次结果；
  3. **数据库终态只发生一次变更**：目标对象/单据数量 = 1（而非 2），库存/SLE/Bin 流水无重复（如 `Stock Ledger Entry` 仅一套）。
- **可复算口径**：以「对象/单据计数、流水计数」为断言，不以 agent 自评「我认为是重试」为通过依据。

## 8. 「合法重复业务如何表达」的可执行验收方法（W10）

对应「独立合法重复业务不被误合并」，对 create 组至少 1 题：

- **表达方式**（依 D02 冻结，三选一或组合）：(a) 提供不同业务引用号（进指纹）；或 (b) 窗口期外两次调用（第二次不命中）；或 (c) 显式改变任一进指纹的业务字段。
- **断言**：两次调用均成功，终态 = **2 个独立对象/单据**（不被合并）；流水/SLE 各计两套。
- **反向校验**：同一验收任务集须同时覆盖 §7（重试只变更一次）与 §8（合法重复不被合并），证明两个方向同时成立，不得只测其一。

## 9. 残余风险与已知限制

1. **误合并残余风险（create 组）**：窗口期（5 分钟）内「同参数合法重复」会被误合并；无业务引用号的对象无法彻底消除此风险，只能通过窗口期缩短 + #26 批次状态查询缓解。这是「无可信关联信号」的必然结果，须在符合性声明中如实记录。
2. **`claudecode/toolUseId` 出现不稳定**：实测在单次调用/重试轮次的 `_meta` 中出现、在多调用同轮次（基线）未出现；且为客户端特定字段，**不得**作为幂等实现依据（§6.2）。
3. **超时未测得上限**：70s 慢响应未触发超时，Claude Code 覆写了 SDK 60s 默认值，其真实 MCP 超时上限本包未测出（对本结论无影响——超时不重发已由静态+动态共同确认）。
4. **断线后模型重试未在本包内强制触发**：crash 场景模型仅询问未自动重试；无论模型后续是否重试，该重试均为新请求、无关联信号，不影响 §3/§4 结论。
5. **结论仅适用于 Claude Code 2.1.263 / stdio / MCP 2025-11-25**；更换客户端（含 VS Code 扩展、streamable HTTP 传输）须重新起算核查（总则 §12），streamable HTTP 下存在 `sessionId`/`resumptionToken`，其关联语义须另行调研。
6. **SDK 版本**：静态分析基于独立 `@modelcontextprotocol/sdk` v1.29.0；Claude Code 内置编译 SDK 版本不可单独读取，重试结论以「SDK 源码语义 + Claude Code 实测行为」双证据共同支撑。

**结论一句话**：在 Claude Code 2.1.263 / MCP 2025-11-25 / stdio 下，`tools/call` 无传输/SDK/harness 层透明重试，亦不存在「合规可信且跨重试可关联」的信号；幂等必须依赖 server 侧业务参数指纹 + 状态断言（confirm/cancel）+ 窗口期缩短（create 组 300s / confirm·cancel 组 60s）+ 业务引用号（可选），并如实记录误合并残余风险。
