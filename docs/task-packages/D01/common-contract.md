> **文档性质**：D01 交付物 CD-2，《MCP 公共契约与错误模型》正文。它是 D02 冻结 26 个业务 tool（PRD §3.3 #1–#26）各自契约的统一基座，只规定**所有 tool 共享的契约层**，不含任何具体业务 tool 的业务语义、name、description、schema 或断言。
> **版本**：v1.0（D01 实施产出，待 Implementation Reviewer 评审通过后作为 D02 权威输入）。
> **上游依据**：《开源后端 Agent 化接入规范》2026-09-07 定稿版（下文「规范 §x」）；《ERPNext-MCP 改造 PRD》2026-09-12-r1（下文「PRD §x」）；《MCP 改造任务包总则》v1.1（下文「总则 §x」）；B01–B04 interface-facts v1.0（均已封存，下文「B0x Fn」）；B05 v1.0（已封存，`idempotency-research.md` 与 `task.md` §18.3，下文「B05 §x」）。
> **约束性等级**：MUST / MUST NOT / SHOULD / SHOULD NOT / MAY 沿用规范 §0.1 口径。无标注段落为说明性文字。
> **消费方**：D02（直接消费）；经 D02 间接传递至 E01、F01/F02/F04。E02 与本包为「共同对齐 B05 §18.3、保持一致」关系，非上下游（总则 §13）。

## 0. 阅读约定与本契约的抽象层级

本契约是**跨 tool 共享口径**，不是任何单个 tool 的契约。凡涉及「某个具体 tool 的 name / description / 输入输出 schema / annotation 取值 / 前置断言 / 幂等参数范围」，均属 D02 逐 tool 冻结范围，本契约不写死。本契约条款正文 MUST NOT 出现具体 tool 的业务语义；举例与事实引用（如对象类型名、错误码）下沉到「说明：」段落或来源索引，用于可复核性，不构成对单个 tool 契约的冻结。

本契约只回答「所有 tool 共同的『接得对不对』口径」，与规范 §3.4 分工一致：规范回答「怎么算对」，PRD 回答「这次做什么」，本契约回答「D02 逐 tool 契约之上、所有 tool 共享的那一层口径」。

## 1. 命名与 tool 标识规范

**对应 D01 task §9.1 第 1 项；依据规范 §8.2/§8.3、PRD §3.2/§3.3。**

1. **命名空间方案**：`erpnext_<资源>_<动作>`。前缀命名空间 `erpnext_` + 资源分组 + 统一动作后缀（PRD §3.2）。
   - 选资源分组（而非服务分组）的理由：同一业务对象的动作聚簇，agent 按对象定位 tool 的路径最短（PRD §3.2）。
   - 命名 MUST 有命名空间，且同一后端内 MUST 保持一致（规范 §8.2）。

2. **动作后缀语义**（统一口径，PRD §3.2 + §3.3 归纳）：
   | 后缀 | 语义 | 读写性质 |
   |---|---|---|
   | `create` | 创建**草稿**（主数据 create 为登记新对象；单据 create 仅产生草稿态、无业务效果） | 写 |
   | `confirm` | **生效**（草稿 → 已生效，触发真实业务效果/库存变动） | 写 |
   | `cancel` | **取消**（已生效 → 已取消，冲回业务效果） | 写 |
   | `plan` | **只出方案**（只读现状并产出执行方案，不产生写入） | 读+方案 |
   | `search` / `get` / `query` | **读**（检索 / 查阅详情与状态 / 查询库存或流水） | 读 |

   > 说明：`search`/`get`/`query` 均由 D01 自 PRD §3.3 工具清单归纳为「读」后缀，不写死单个 tool 名。动作后缀与**自主度档位**的对应（全自动/人确认/只出 plan）由 §10.2 三条逐操作推导，不由后缀直接决定——同是 `create`，单据草稿与主数据的档位可能不同（PRD §4.1）。

3. **相近 tool 消歧**（规范 §8.3）：语义相近、agent 可能混淆的 tool，MUST 在 description 中写明「什么情况下不该用这个、该用哪个」。
   - 消歧文案写入 description，是本契约对 D02 逐 tool description 的通用要求；消歧对（如 create vs update、create vs confirm 等）的**具体内容**由 D02 依 PRD §3.4 逐 tool 冻结，本契约不枚举。

4. **命名可调项边界**（PRD §3.2 / 规范 §8.2）：命名方案属验收迭代可调项。跑题显示选错率集中时，优先调前缀/后缀，**不动 tool 语义**。调整命名不改本契约，也不改 PRD 冻结语义。

## 2. 公共 schema 规范

**对应 D01 task §9.1 第 2 项；依据规范 §8.4/§8.5、PRD §2.3。**

### 2.1 输入参数通用形状

1. **必填/可选标识**：每个参数 MUST 显式标明必填或可选；必填缺失与格式错误按第 4 节「参数缺失/格式错误」返回可自纠报错，MUST NOT 静默使用默认值或猜测。
2. **嵌套行项目结构**：必要单据子表（Sales Order Item、Purchase Order Item、Purchase Receipt Item、Delivery Note Item、Stock Entry Detail、Stock Reconciliation Item 等）只能作为其**父单据 tool 的嵌套行项目**读写，不视为独立操作对象，不得作为 `target_object` 独立查询或修改（PRD §2.3）。行项目字段的稳定排序与归一化，供幂等指纹与断言使用（见第 5、6 节）。
3. **Link 字段引用表达**：引用值以**语义标识**表达（如物料以物料编码、仓库以仓库名等业务可读标识），由 **server 解析为后端标识**；MUST NOT 要求 agent 填后端内部标识符（规范 §8.4/§8.5、PRD §2.3）。
4. **参数命名无歧义**（规范 §8.4）：参数名必须能让 agent 从 description 直接判断该填什么，无需查后端文档。
5. **禁止任意字段名/DocType**：server 不得接受任意字段名或任意 DocType；可写字段及 Link 字段允许目标由 D02 逐 tool 冻结（PRD §2.3、第 7 节）。

### 2.2 返回结构通用形状

1. **高信噪比**：返回值 MUST 只保留高信噪比信息，MUST NOT 返回低层技术标识符（规范 §8.5）。
2. **语义化标识**：内部标识符 MUST 解析成语义化表达或有序编号后再返回（规范 §8.5）。
3. **分页/过滤/截断/详略**：MUST 组合使用分页、范围选择、过滤、截断，并配合合理的默认值（规范 §8.5）；结果集可能显著膨胀的查询类 tool SHOULD 提供详略枚举参数（简略/详细）。返回值上限参考默认值约两万五千 token（设计默认值，非验收阈值，规范 §8.5 说明）。
4. **写操作返回值契约**：成功响应须符合声明的返回契约；返回值符合 schema 不代表写入成功——写后回读终态由第 6 节事后校验承担（规范 §9.5）。

## 3. annotation 规范

**对应 D01 task §9.1 第 3 项；依据规范 §8.1。**

1. **四个 annotation 全部显式声明**：只读（readOnly）、破坏性（destructive）、幂等（idempotent）、与外部世界交互（openWorld）四个布尔提示 MUST 全部显式声明，MUST NOT 依赖协议默认值（规范 §8.1）。协议层 annotation 留空的语义是「未知」，会迫使客户端保守处理、分级退化为全人确认。

2. **对外声明与对内执法分离**（规范 §8.1/§9.1）：annotation 是对外声明，供客户端做交互决策，**无强制力**；强制力 MUST 由 server 侧实现承担。任何机制只做声明不做实现，视为未实现（规范 §9.1）。

3. **旁挂后端「与外部世界交互」= 否**：对旁挂自有后端的场景，「是否与外部世界交互」字段 MUST 声明为否（规范 §8.1）。后端是封闭业务域，网络调用只是接入方式，不是语义边界；口径统一可避免客户端交互策略漂移。

4. **`idempotent`（幂等声明）与幂等实现的对应关系**：
   - 对外 `idempotent=true` 的 tool，对内 MUST 由 server 侧依第 5 节幂等边界实现（指纹/状态断言/窗口期），不得仅靠声明。
   - 未实现幂等机制的写 tool 不得声明幂等；幂等声明与实现不一致属失败路径（规范 §12.3 第五类）。
   - 只读 tool 天然幂等，但只读声明（readOnly=true）与幂等声明是两回事，MUST 分别显式声明。

## 4. 公共错误模型

**对应 D01 task §9.1 第 4 项；依据规范 §8.6、PRD §7、B01–B04 接口事实错误结论（B01 F1/F2/F3/F4、B02/B03/B04 §6）。**

> 范围边界（D01 task S04）：本模型只覆盖 PRD §7 中**属于错误响应**的场景。批次查询（读能力）、异常回滚（管理员运维、非 MCP tool）、确认降级（L2 受限形态的系统性 fail-closed）为**非错误口径**，不入本模型。

### 4.1 统一错误响应形状

每个错误响应 MUST 包含以下字段，不得只给不透明错误码或堆栈（规范 §8.6）：

| 字段 | 含义 | 要求 |
|---|---|---|
| `isError` | 协议层错误标记 | 恒为 `true` |
| `code` | 稳定语义化错误码 | 面向 agent 可判读；MUST NOT 直接以后端原生异常名作为唯一码 |
| `message` | 可读说明 | MUST 传达**具体可行的改进方向（下一步该怎么做）**；MUST NOT 只给状态码/堆栈 |
| `retryable` | 是否可安全重试 | 供 agent 判断能否不改输入直接重试；后端不可达时写操作 MUST 标记为不自动重试（总则 §6.10） |
| `details` | 结构化上下文（可选） | 如缺口数量与可用量、当前状态、所需权限、合法取值等 |

**透出边界**（规范 §8.6、PRD §7）：MUST NOT 透出完整堆栈、后端内部标识符、认证信息或未授权业务数据。后端原生异常名/HTTP 状态码可作参考附注透出（如 `TimestampMismatchError`/417），但 MUST 转译为业务语义并配自纠建议后一并给出，不得裸抛。

### 4.2 错误分类枚举与统一响应形状

| 错误类 | 语义化 `code` | 事实来源（后端原生异常 → HTTP） | `message` 自纠要点 | `retryable` |
|---|---|---|---|---|
| 参数缺失/格式错误 | `invalid_argument` | server 层 schema 校验（规范 §8.6、PRD §7） | 指出缺失/非法参数与合法格式 | 可（改参数后） |
| 前置断言失败（业务状态） | `precondition_failed` | `DocstatusTransitionError` 417、`LinkExistsError` 417 等（B02/B03/B04 §6） | 返回**当前状态 + 建议动作** | 视场景（状态变化后可能可重试） |
| 重名（主数据） | `duplicate_name` | `DuplicateEntryError` 409（B01 F1） | create 报错并指向 update；update 要求标识精确（PRD §7） | 否（须改目标标识） |
| 并发冲突 | `concurrency_conflict` | `TimestampMismatchError` 417（B01 F2、B02/B03/B04 F2） | 建议**重读后重试** | 可（重读取新 `modified` 后） |
| 越权 | `permission_denied` | `PermissionError` 403 等（B04 F3、PRD §5.6） | 转译列出**所需权限/对象**，不透出堆栈 | 否 |
| 后端不可达 | `backend_unavailable` | —（server 侧判定，PRD §7） | 明确报「后端不可达」；写操作 MUST NOT 由 server 自动重试（总则 §6.10） | 否（写不自动重试） |
| 结果集超限 | `result_set_overflow` | —（server 侧判定，PRD §7、规范 §8.5） | 截断 + 分页/过滤提示 | 可（加过滤后） |

> 说明：上表后端原生异常→HTTP 状态码为 B01–B04 已封存事实（`DuplicateEntryError` 409、`TimestampMismatchError` 417、`LinkValidationError` 417、`ValidationError` 417、`DocstatusTransitionError` 417、`LinkExistsError` 417、`DoesNotExistError` 404、`PermissionError` 403 等）。D01 不重新实测；转译口径以上游接口事实为准。

### 4.3 幂等命中（非错误，特殊成功响应）

幂等命中**不是错误**，是成功语义（B05 §18.3 第 5 条、D01 task §9.1 第 4 项）。其统一响应形状：

| 字段 | 含义 |
|---|---|
| `isError` | `false` |
| `idempotent_replay` | `true`（标记「重复请求已按幂等合并」） |
| 结果 | 返回**首次结果**（与首次成功调用一致） |
| `message` | 附「重复请求已按幂等合并」说明 |

confirm/cancel 组的状态断言命中同样返回「已在目标状态」的幂等成功（非通用错误），其**具体返回结构由 D02 冻结**（B05 §18.4 第 2 条、第 5 节）。

### 4.4 通用约束

- 报错响应 MUST 传达具体可行的改进方向，MUST NOT 只给不透明错误码或堆栈（规范 §8.6）。
- 失败路径 MUST NOT 静默成功；错误 MUST NOT 以成功响应伪装（规范 §8.6/§9.5、总则 §6.10）。
- 返回值的 schema 校验不适用于错误响应——只有成功响应才校验返回值契约（规范 §9.5 说明）。

## 5. 幂等边界契约

**对应 D01 task §9.1 第 5 项；依据 B05 §18.3、B05 idempotency-research §4/§6/§7/§8、PRD §5.1、规范 §9.3。**

本契约将 B05 冻结结论落地为契约口径，**只冻结「做什么口径」，不冻结实现手法**（E02 职责）。

1. **窗口期冻结值**（B05 §18.3 第 3 条；E02 实现不得放宽，缩短须走变更控制）：
   | 组 | 窗口期 |
   |---|---|
   | create 组（主数据 create；单据/收货/发货/调拨草稿 create） | **300 秒（5 分钟）** |
   | confirm/cancel 组（生效与取消） | **60 秒** |

2. **指纹规则**（B05 §18.3 第 4 条、规范 §9.3、PRD §5.1）：
   - 幂等指纹 MUST 由 **server 依业务参数规范化**（稳定排序 + 归一化）计算，agent 完全不感知。
   - tool MUST NOT 向 agent 暴露幂等键参数；MUST NOT 接受客户端传入的幂等键覆盖 server 生成的指纹。
   - **传输/客户端字段不进指纹**：`id` / `progressToken` / `claudecode/toolUseId` 及 agent 随机 request id/幂等键，一律不参与指纹、不得成为可信覆盖值（规范 §9.3、B05 §18.3 第 2 条）。
   - **同参同指纹、异载异指纹**：相同业务参数（键序不同）→ 同指纹；不同有效负载 → 不同指纹。
   - 进指纹 = **影响业务终态**的业务参数；不进指纹 = 不影响业务终态的展示性备注 + 传输/客户端字段。**具体哪些参数进指纹**（各 tool 组的进指纹参数清单）由 D02 依 PRD §5.1 逐 tool 冻结，本契约只规定上述公共规则。

3. **confirm/cancel 状态断言兜底**（B05 §4 第 1 条、PRD §5.1/§5.2）：
   - confirm 仅接受草稿状态；cancel 仅接受已生效状态。
   - 状态断言命中时 MUST 返回**幂等成功**（「目标单据已在目标状态，本次视为重复请求已合并」），MUST NOT 返回通用前置断言错误——否则 agent 会把幂等命中误判为失败并反复自纠。
   - confirm/cancel 组无合法重复业务（同一单据不能合法 confirm/cancel 两次），窗口期仅用于并发/在途重复提交的去重。

4. **误合并策略**（create 组，B05 §4 第 2 条）：窗口期内同参数命中 → 返回首次结果 +「重复请求已按幂等合并」；误合并的残余风险通过批次状态查询暴露（agent 可查「是否已建过这笔」），由 agent 自行核对后再决定是否补建。

5. **合法重复业务表达**（仅 create 组，B05 §8）：独立合法重复业务不得被误合并。表达方式三选一或组合（由 D02 逐 tool 冻结）：(a) 不同业务引用号（进指纹）；(b) 窗口期外两次调用；(c) 显式改变任一进指纹的业务字段。

6. **不绑定传输层字段**（规范 §9.3、B05 §18.3 第 2 条）：不得以 `id`/`progressToken`/`claudecode/toolUseId` 等传输层或客户端字段作幂等或契约依据。幂等关联信号不存在（B05 实测：无可信且跨重试可关联的信号），故幂等只依赖 server 侧业务参数指纹 + 状态断言 + 窗口期 + 业务引用号（可选）。

7. **残余风险如实记录**：create 组「窗口期内同参数合法重复被误合并」是「无可信关联信号」的必然结果，须在符合性声明中如实记录（B05 §9 第 1 条）。

## 6. 前置断言 / 事后校验 / 批次台账公共口径

**对应 D01 task §9.1 第 6 项；依据规范 §9.4/§9.5/§9.6、PRD §5.2–§5.4、B01–B04 事务/原子性/乐观版本断言结论。**

### 6.1 前置断言：两层拆分（规范 §9.4）

| 层 | 内容 | 是否协议已覆盖 |
|---|---|---|
| schema 层 | 参数格式是否合法 | 已覆盖（协议要求 server 校验参数并以业务错误形式返回） |
| 业务状态层 | 当前状态是否允许此操作 | **未覆盖**（这才是本规范所指的前置断言） |

**完成参数 schema 校验不构成满足前置断言要求。** 业务状态断言（如「同名对象不存在」「来源单据已生效」「目标仍为草稿」等）由 D02 依 PRD §5.2 逐 tool 冻结；本契约只冻结「两层拆分、schema 校验不计入」的公共口径。

### 6.2 事后校验：两层拆分（规范 §9.5）

| 层 | 内容 | 是否协议已覆盖 |
|---|---|---|
| 返回值形状 | 返回结构是否符合声明的契约 | 已覆盖 |
| 写入是否落库 | 数据是否真的变成了期望终态 | **未覆盖**（这才是本规范所指的事后校验） |

**返回值符合 schema 不代表写入成功。** 每个写 tool 执行成功后，server MUST 回读目标对象并断言期望终态；回读不一致 → 按第 4 节报错、记入批次台账并标记待回滚（PRD §5.3）。写操作成功响应前 MUST 完成事后回读（总则 §6.10）。

### 6.3 乐观版本断言口径（B01–B04 F2 一致结论）

- **写 tool 必须携带 `modified` 做乐观并发，否则无并发保护**——这是跨 tool 的 MUST 级硬口径（B01 F2、B02 F2、B03 F2、B04 F2 实测一致：`modified` 为可选并发令牌，提供则校验、省略则不校验）。
- 版本断言与写入 MUST 由同一后端事务或等价原子方法完成（PRD §5.2/§5.5）；不得以 MCP 层「先查询、后调用提交」的两个远程请求冒充同一事务。
- 具体每个 tool 的 `modified` 语义由 D02 逐 tool 冻结（D01 task §16）。
- 已知事实（供 D02 处理，D01 不预设实现手法）：标准 cancel 端点不接受 `modified`，仅 `frappe.client.save`（docstatus=2 + modified）等价路径可施加版本保护（B02 F3、B03 F3、B04 F3）；是否对 cancel 施加版本保护由 D02 逐 tool 明确。

### 6.4 批次台账公共口径（规范 §9.6、PRD §5.4）

1. **批次粒度**：一次 `tools/call` 一个批次，server 生成批次标识；单次调用产生的全部变更同批。
2. **台账独立留存**：批次台账由 server 独立留存（参数指纹、涉及单据编号、时间、会话），不依赖后端。
3. **回滚路径**：草稿 → 删除；已生效 → 后端原生取消；已取消 → 终态不可回滚，台账如实标注。
4. **`batch_status_get` 可见性边界**：agent 只能经批次状态查询 tool 读取**归属于自身可信调用方身份**的批次及状态（读），不能主动发起回滚；不得查看其他调用方的批次参数、涉及单据与回滚信息（PRD §5.4、总则 §6.10「普通调用方不得读取其他调用方的批次信息」）。
5. **跨 tool 业务流不合并批次**（订单 → 收货 → …），聚合回滚为二期（PRD §5.4）。
6. 批次 Owner 持久化、跨会话查询授权与审计规则以 B00 身份结论为前提，由 E02 冻结（总则 §13）；本契约不预设 E02 实现手法。

### 6.5 事务与原子性公共口径（B01–B04 §3 一致结论）

- 单张单据/主数据的 create/confirm/cancel 均为单次后端事务；关键 confirm 状态校验必须与实际提交处于同一后端事务（或等价原子方法）。
- 后端原生提交校验作为最终防线；乐观版本断言失败时无部分写入。
- 跨单据流程天然跨调用，MCP 侧不引入跨调用事务，一致性由前置断言 + 事后校验 + 批次台账承担（PRD §5.5）。

## 7. 窄接口与允许清单边界

**对应 D01 task §9.1 第 7 项；依据规范 §9.6、PRD §2.3/§5.6、总则 §6.10。**

1. **两张允许清单边界**（PRD §2.3）：
   - **操作允许清单**（12 类业务对象）：允许 agent 经明确授权的 tool 对其执行文档规定的业务动作。清单外对象 MUST NOT 经任何 tool 读或写。
   - **引用允许清单**（9 类依赖对象）：只允许作为业务 tool 的参数引用（用于前置断言校验、单据 link 字段），**不允许**经 MCP 直接创建、修改、删除；由 server 配置或后端预置。
   - 两张清单变更均走 PRD 变更流程并重新验收（PRD §2.3）；本契约不得反向放宽（总则 §6.10）。

   > 说明：12 类操作对象 = Customer、Supplier、Item、Item Price、Sales Order、Purchase Order、Purchase Receipt、Delivery Note、Stock Entry、Stock Reconciliation、Bin、Stock Ledger Entry（PRD §2.1）。9 类引用对象 = Company、Warehouse、Price List、Currency、Customer Group、Supplier Group、Territory、Item Group、Unit of Measure（PRD §2.3）。清单的最终成员与「哪些对象接、哪些不接」由 PRD 冻结，D02/E01 逐项落地；本契约只冻结「清单外 MUST NOT 读写、引用清单只可引用不可增删改」的公共边界。

2. **Link 字段目标仅限引用允许清单**：Link 字段允许目标 MUST 限于引用允许清单；不得指向操作清单外的对象（如财务/制造/系统管理对象，PRD §2.2）。

3. **禁止任意字段名/DocType**：server 不得接受任意字段名或任意 DocType；可写字段与 Link 允许目标由 D02 逐项冻结（PRD §2.3）。

4. **子表仅作父单据嵌套**：Contact、Address 等不纳入两张清单；必要单据子表只能作为父单据 tool 的嵌套行项目读写，不视为新增独立操作对象（PRD §2.3）。

5. **每个 tool 最小权限与最小参数**（规范 §9.6、PRD §5.6）：每个 tool 只暴露其业务动作所需的**最小参数与动作**，且 description MUST 声明窄接口边界；专用系统账号 + 专用角色，权限收敛到各操作允许对象按其声明能力所需的读/写权限 + 引用允许清单对象的读。越权由后端原生权限拒绝，tool 转译为第 4 节的可自纠报错（PRD §5.6）。

6. **不新增通用执行面**：MUST NOT 新增通用 CRUD 或任意代码执行面（总则 §6.7、PRD §3.1）；通用查询能力仅在 tool 实现内部复用，不作为 tool 执行面暴露。

## 8. 跨口径不变量（汇总）

以下不变量对任何正常路径、失败路径、重试路径均 MUST 成立（总则 §6.10 + D01 task §10）：

1. 两张允许清单之外的对象不可被操作或引用；引用允许清单对象只可引用、不可经 MCP 增删改。
2. 人确认操作未经有效 server 侧确认不得写入（规范 §9.7）。
3. 按 B05 冻结的「同一业务意图」判定规则，重复重试最多产生一次业务变化；独立的合法重复业务不得被幂等机制合并。
4. 写操作成功响应前必须完成事后回读（写后回读终态）。
5. 普通调用方不得读取其他调用方的批次信息。
6. 后端不可达时不得自动重试写操作。
7. 错误不得以成功响应伪装，失败路径不得静默成功。
8. 公共契约不绑定具体传输层字段（`id`/`progressToken`/`claudecode/toolUseId` 等）。
9. 幂等边界不得反向放宽 B05 冻结值（窗口期 create 300s / confirm·cancel 60s、指纹规则）。
10. 未经实测/未经上游冻结结论的表述不得写入契约（不以推测代替结论）。
