# 开源后端 Agent 化接入规范

**文档性质**：规范（specification）。定义"接得对不对"的判定标准，不定义"这次要做什么"。

**适用对象**：从公开代码仓库获取的开源业务系统，需要被通用 agent 调用以处理业务的场景。

**下游关系**：具体系统的改造 PRD 引用本规范，本规范不引用任何 PRD。两者的职责边界见第 3.4 节。

---

# 0. 阅读约定

本章必须先读，后续所有条款按此约定解释。

## 0.1 约束性等级

| 等级 | 含义 |
|---|---|
| MUST / MUST NOT | 必须遵守，不遵守即不符合本规范 |
| SHOULD / SHOULD NOT | 建议遵守，偏离须在符合性声明中书面说明理由 |
| MAY | 可选 |

无标注的段落是说明性文字，不产生约束力。

说明：本规范的制定方不参与实施，条款的强制力必须写在纸面上。没有标注等级的规则，实施方一定会自行解释。

## 0.2 正文抽象、说明块具体

- 条款正文 MUST NOT 出现任何具体系统的专有概念。出现即说明该条抽象不干净，须重写。
- 所有举例一律下沉到「说明：」开头的段落。
- 条款的抽象性与 checklist 的可操作性冲突时，以本约定解。

## 0.3 本规范定义什么

本规范定义的是**什么样算接好了**：接入顺序、tool 设计约束、写操作保障机制、自主度分级标准、验收口径。

本规范不定义某个后端这次接到哪一级、接哪些对象、清哪些数据、指标阈值定多少——那些是实施层决策，由具体系统的改造 PRD 或接入方案定义。

凡形如「本期要不要做 X」的问题，本规范一律不答，只定义「X 做了之后怎么算合格」。

## 0.4 "不规定"与"未覆盖"

本规范中「由实施方定义」表示有意留出的自由度，实施方须自行定义并记录；「本规范未覆盖」表示该问题不在本规范范围内。两者含义不同，MUST NOT 混用。

# 1. 背景与目标

## 1.1 背景

开源业务系统提供了完整的数据模型和原生 API，但这些接口是为人操作的界面和为程序调用的集成设计的，不是为 agent 设计的。直接把 API 端点包装成 tool，agent 会选错工具、填错参数、被无关数据撑爆上下文；一旦放开写权限，还会出现无法追溯和无法回滚的数据变更。

目前缺少一套可复制的接入方法：拿到一个开源后端，按什么顺序做、tool 怎么划分、写操作怎么保障、接完怎么验证。每个项目从头摸索，结果无法横向复用，出了问题也无法归因到具体环节。

## 1.2 目标

- ✅ 开源后端部署后，按本规范旁挂 MCP server，即可被通用 agent 调用处理业务、写入和管理数据
- ✅ 换一个没接触过该后端的人，拿本规范能独立完成接入
- ✅ 接入结果可客观验收，不依赖主观判断和 agent 自评
- ✅ 规范本身与具体后端解耦，第二个项目不必从头摸索

## 1.3 条款准入标准

判断一条规则该不该进本规范，只看一条：**换一个开源后端是否仍然成立**。只对某一个系统成立的技巧不写。

# 2. 术语

| 术语 | 定义 |
|---|---|
| **tool** | 一个可被 agent 调用的业务动作，包含 name、description、参数 schema、可选的返回值 schema |
| **annotation** | 附在 tool 上的四个布尔行为提示：是否只读、是否破坏性、是否幂等、是否与外部世界交互。供客户端决定交互方式 |
| **通用执行面** | 后端自带的、可表达任意操作的入口，如脚本引擎、通用查询接口、命令行 |
| **自主度档位** | 单个写操作的人工介入程度，分全自动、关键步骤人确认、只出 plan 三档。见第 10 章 |
| **符合性等级** | 一次接入整体达到的能力级别，分 L1/L2/L3 三级。见第 3 章 |
| **窄接口** | tool 只拥有完成其任务所需的最小权限，且可执行动作的范围与类型受限 |
| **幂等指纹** | 由 server 依据业务参数计算的值，用于识别同一业务意图的重复调用 |
| **前置断言** | 执行前对**业务状态**的检查，判断当前状态是否允许此操作。不含参数格式校验 |
| **事后校验** | 执行后回读数据，确认写入是否真的落库为期望终态。不含返回值格式校验 |
| **可回滚批次** | 一组变更共享的批次标识，配合可执行的回滚路径，使该组变更可整体撤销 |
| **验证任务集** | 按第 12 章方法生成并冻结的一组题目，每题含初始态、指令、期望终态断言 |
| **符合性声明** | 接入方交付的书面声明，写明本次接入达到的等级、启用的档位、裁剪的条款及理由 |

档位与等级的区别：**档位是单个操作的属性，等级是整次接入的属性**。一次 L3 接入中，不同操作仍可分处三个不同档位。

# 3. 适用范围与符合性等级

## 3.1 为什么分级

不同接入的风险差别极大：一个只出报表的接入和一个能改库存的接入，需要的保障机制完全不同。若所有条款一律生效，实施方只有两个选择——全做（做不完）或自行删减（无记录）。本章定义分级与裁剪规则，使裁剪成为有依据、可追溯的动作。

## 3.2 三个等级

| 等级 | 名称 | 能力范围 |
|---|---|---|
| **L1** | 只读接入 | agent 只能查询、汇总、分析，不提供任何写操作 tool |
| **L2** | 受控写入 | 提供写操作 tool，但全部处于「关键步骤人确认」或「只出 plan」档 |
| **L3** | 自主写入 | 存在处于「全自动」档的写操作 tool |

等级由**实际启用的最高档位**决定，不由意图决定。只要存在一个全自动档的写 tool，该次接入即为 L3，须满足 L3 全部条款。

## 3.3 条款生效范围

| 章节 | L1 | L2 | L3 |
|---|---|---|---|
| 第 6 章 接入形态 | MUST | MUST | MUST |
| 第 7 章 接入 checklist | MUST | MUST | MUST |
| 第 8 章 tool 设计规范 | MUST | MUST | MUST |
| 第 9 章 写操作规范 | 不适用 | MUST（按档位表裁剪） | MUST（全部） |
| 第 10 章 自主度分级 | 不适用 | MUST | MUST |
| 第 11 章 数据治理流程规范 | 涉及治理时 MUST | 涉及治理时 MUST | 涉及治理时 MUST |
| 第 12 章 接入验收流程规范 | MUST | MUST | MUST |
| 第 13 章 指标口径 | MUST | MUST | MUST |

第 6、7、8、12 章为**全等级基线**，任何等级都不得裁剪。

说明：tool 设计规范和验收流程之所以不随等级放宽，是因为它们解决的是"agent 能不能用对"，这个问题在只读接入中同样存在，且只读接入用错工具同样会给出错误结论。

## 3.4 与具体系统改造 PRD 的边界

本规范与下游 PRD 的分工如下。同一件事 MUST NOT 在两处重复定义。

| 事项 | 本规范定义 | 具体系统改造 PRD 定义 |
|---|---|---|
| 接入顺序 | ✅ checklist 骨架 | 每步的具体执行内容 |
| 纳入范围 | ❌ | ✅ 哪些业务对象接、哪些不接 |
| tool 划分 | ✅ 划分原则与约束 | ✅ 该系统实际拆成哪几个 tool |
| 命名方案 | ✅ 须有命名空间、须一致 | ✅ 选按服务分组还是按资源分组 |
| 保障机制 | ✅ 五个机制的定义与档位要求 | ✅ 各机制在该系统的实现方式 |
| 档位归属 | ✅ 判定依据与推导方法 | ✅ 具体某个操作归哪一档 |
| 符合性等级 | ✅ 等级定义与条款范围 | ✅ 本次接入做到哪一级 |
| 幂等指纹范围 | ✅ 须由 server 生成、须文档化 | ✅ 哪些参数进指纹、窗口期多长 |
| 验收题目 | ✅ 生成方法与覆盖下限 | ❌ 题目由 coding agent 生成，不写进 PRD |
| 指标 | ✅ 口径 | ✅ 阈值 |
| 数据治理 | ✅ 流程骨架与产出物要求 | ✅ 清哪些数据、怎么清、谁验收 |

一句话分界：**本规范回答"怎么算对"，改造 PRD 回答"这次做什么"。**

## 3.5 符合性声明

接入方 MUST 随交付物提交符合性声明，内容包括：

1. 本次接入的符合性等级
2. 实际启用的档位清单，及每个写操作 tool 的档位归属
3. 每一条 SHOULD 级条款的遵守情况；偏离的须说明理由
4. 判定为"不适用"的条款及理由

条款不适用时 MUST 书面说明，MUST NOT 静默跳过。

说明：静默跳过与显式裁剪的区别不在于最终做了多少，而在于三个月后能不能查清当初为什么没做。

# 4. 引用标准与版本

本规范依赖以下外部标准。接入时 MUST 核对实际版本，版本不一致时以实际版本为准，并在符合性声明中记录。

| 引用对象 | 用于 | 版本处理 |
|---|---|---|
| MCP 协议规范 | tool 定义、annotation 字段、参数校验要求、返回值契约、server 侧确认机制 | 按接入时的协议版本文档为准；协议版本升级时 MUST 复核第 8、9 章 |
| 幂等键相关公开草案 | 第 9.3 节幂等实现的参考依据 | 仅作参考，MUST NOT 绑定其具体传输层字段 |
| 公开的 MCP 安全实践清单 | 第 9.6 节最小权限、第 9.7 节确认内容要求 | 作为依据引用，不逐条照搬 |

外部标准升级时的处理：MUST 重新核对本规范中标注了「协议已覆盖」的条款（第 9.4、9.5 节），确认覆盖范围是否变化。**覆盖范围扩大不自动放宽本规范的要求**，须经本规范修订后生效。

说明：这一条防的是"协议新版本加了个字段，现场就认为某条机制不用做了"。协议提供的是声明能力，本规范要求的是实现能力，两者不能互相替代。

# 5. MCP 最简说明

面向不熟悉 MCP 的读者，只讲理解本规范所需的部分。

MCP 是一套让 agent 调用外部能力的通用协议。server 声明一组 tool，客户端（agent 所在的应用）读取这些声明，由模型决定调用哪个、传什么参数。协议的价值在于通用：任何支持 MCP 的客户端都能接同一个 server，不需要为每个 agent 单独开发。

理解本规范需要三个概念，其定义见第 2 章：tool、annotation、server 侧确认机制。

协议细节不在本规范展开，按接入时的协议版本文档为准。

# 6. 接入形态

## 6.1 前提

**必须满足**

- 后端有可用的原生 API，覆盖目标业务对象的读写
- 后端权限模型可按调用方粒度配置
- 后端数据库可重置到指定快照
- 接入方可提供独立验收环境

**最好满足**

- 后端 API 有可读的数据模型文档或源码
- 目标客户端支持 server 侧发起的确认机制

## 6.2 形态约束

- MCP server MUST 以独立进程旁挂后端原生 API，MUST NOT 修改后端源码。
- MUST 只使用通用 MCP 协议，MUST NOT 自研接口协议、MUST NOT 开发前端界面。
- MUST NOT 依赖特定模型特性、特定客户端 UI、特定提示词。

说明：「不依赖特定客户端」约束的是**被验收的 agent**，不约束生成验收标准时使用什么工具。这两者必须分开，否则会被误判为自相矛盾。

## 6.3 终态

agent 自主 plan、连续执行多步操作完成业务任务，而非由人一步步喂指令。

# 7. 接入 checklist

## 7.1 第一步：判断通用执行面（分叉点）

MUST 作为 checklist 的第一步执行，MUST NOT 后置。

| 判断结果 | tool 划分方式 |
|---|---|
| 存在通用执行面 | 少数几个 tool 即可覆盖 |
| 不存在 | MUST 按业务任务拆分结构化 tool |

> 这不是风格选择，是被后端性质决定的。放在后面做，前面所有 tool 划分工作都要返工。

说明：某些开发工具类 agent 只用两个工具就能工作，是因为命令行本身就是通用执行面，读取靠命令、修改靠补丁；企业业务系统通常没有这种东西，只能按任务拆。

## 7.2 后端侧准备

1. 对象裁剪：确定纳入范围的业务对象，其余不接
2. 权限模型配置：按调用方粒度配置最小权限
3. 原生 API 可用性核查：确认目标对象的读写端点齐备
4. 写操作事务边界确认：确认哪些操作是原子的、哪些跨多次调用
5. 数据库可重置到指定快照的可行性确认
6. 独立验收环境准备（见 12.4）

## 7.3 客户端能力核查

MUST 在后端侧准备之后、tool 开发之前执行。

确认目标客户端是否支持 server 侧发起的确认机制。不支持的，该次接入 MUST NOT 使用「关键步骤人确认」档，写操作只能落在「只出 plan」档——即该次接入的符合性等级上限为 L2 的受限形态。

说明：此前置核查不做，人确认档等于没有——写完才发现客户端不支持，整档能力作废。

## 7.4 MCP 侧封装

1. tool 划分
2. 命名与 description
3. 参数语义化
4. 返回值裁剪
5. 报错话术
6. annotation 声明

# 8. tool 设计规范

总原则：**能建在标准之上的就不自己发明，标准没覆盖的才是本规范的增量。**

## 8.1 声明

- 四个 annotation MUST 全部显式声明，MUST NOT 依赖协议默认值。

> 协议层 annotation 是可选的，但留空的语义是「未知」，会迫使客户端保守处理、每次执行前弹窗——分级会全部退化成人确认档，等于没分级。

- **annotation 是对外声明，不是执法机制。** 协议要求客户端将 annotation 视为不可信，因此强制力 MUST 由 server 侧实现承担。
- 「是否与外部世界交互」字段，对旁挂自有后端的场景 MUST 声明为否。

说明：后端是封闭业务域，网络调用只是接入方式，不是语义边界。口径不统一，接入方会各写各的，客户端的交互策略随之漂移。

## 8.2 命名

- 命名 MUST 有命名空间，且同一后端内 MUST 保持一致。
- 具体选按服务分组还是按资源分组，由实施方在验收迭代中确定，本规范不规定。

说明：前缀式与后缀式命名对 agent 选对 tool 的影响并非微不足道，且因模型而异，只能测不能拍。命名方案属于「跑不通就改 tool 定义」中可调的那一侧。

## 8.3 数量

- tool 数量不设硬上限。
- 每个 tool MUST 对应一个完整业务动作。
- MUST NOT 为压低数量而把多个动作塞进一个 tool 再加分支参数。

说明：那是把「选错 tool」的成本转嫁成「填错参数」的成本，更难排查。

- 出现语义相近、agent 可能混淆的 tool 时，MUST 在 description 中写明「什么情况下不该用这个、该用哪个」。

说明：数量少的价值不在于省上下文——按需加载工具定义的方案已经把这个成本压得很低——而在于降低选择成本。tool 越多，agent 选错的概率越高，这与上下文够不够无关。

## 8.4 tool 定义

- tool MUST 按业务任务定义，MUST NOT 只做 API 端点的包装。

说明：与其提供「列用户」「列日程」「建日程」三个 tool，不如提供一个「排日程」——它自己找空档并建日程。前者把编排负担留给 agent，后者把编排下沉进 tool 实现。

- description MUST 按「向团队新人介绍」的标准写：把隐含上下文（查询格式、术语定义、资源之间的关系）显式写出。
- 参数命名 MUST 无歧义。

说明：参数叫 user 不如叫 user_id——前者让 agent 猜该填名字还是标识。

## 8.5 返回值

- 返回值 MUST 只保留高信噪比信息，MUST NOT 返回低层技术标识符。
- 内部标识符 MUST 解析成语义化表达或有序编号后再返回。

说明：把无意义的标识符换成可读名称，能直接降低 agent 的幻觉率——它认不出自己没见过的字符串，但认得出名字。

- MUST 组合使用分页、范围选择、过滤、截断，并配合合理的默认值。
- 返回值上限 SHOULD 设参考默认值，实施方可按后端特点调整。

说明：单次 tool 返回上限的一个可用参考量级是两万五千 token。这是**设计默认值**，不是验收阈值；验收通过线由实施方按业务定。

- 返回值可能显著膨胀的查询类 tool SHOULD 提供详略枚举参数（简略 / 详细）。写操作 tool 不作要求。

## 8.6 报错

- 报错响应 MUST 传达具体可行的改进方向，MUST NOT 只给不透明错误码或堆栈。

## 8.7 静态检查条件

以下四条在 review 时肉眼可判，不依赖跑测试：

| 条件 | 判定 |
|---|---|
| description 不出现后端专有名词 | 出现即不合格 |
| 参数含义可从 description 直接填全，无需查后端文档 | 需查即不合格 |
| 报错信息包含「下一步该怎么做」 | 只报状态码即不合格 |
| description 声明的行为与实际实现一致 | 无法静态查，由验收题覆盖（见 12.3） |

# 9. 写操作规范

**适用范围**：L2、L3。L1 接入不适用本章。

## 9.1 五个保障机制

**通则**：对外声明供客户端做交互决策，无强制力；对内实现是 server 侧的强制约束。任何一条机制只做声明不做实现，视为未实现。

本章两张表的关系：下表管「每一条要做到什么程度」，9.2 的档位表管「哪一档要哪几条」。两表并列，不合并。

| 机制 | 对内实现 | 对外声明 |
|---|---|---|
| 窄接口 | 最小权限、限定可执行动作的范围与类型 | 无标准字段，写入 description |
| 幂等键 | server 依业务参数生成幂等指纹 | 声明为幂等 |
| 前置断言 | 业务状态断言 | 无标准字段，写入 description |
| 事后校验 | 写后回读确认终态 | 声明返回值契约 |
| 可回滚批次 | 批次标识 + 回滚路径 | 如实声明破坏性 |

## 9.2 档位要求

| 机制 | 全自动 | 关键步骤人确认 | 只出 plan |
|---|---|---|---|
| 窄接口 | MUST | MUST | MUST |
| 幂等键 | MUST | MUST | MUST |
| 事后校验 | MUST | MUST | MUST |
| 前置断言 | MUST | SHOULD | SHOULD |
| 可回滚批次 | MUST | MUST | N/A |

说明：窄接口是安全底线；幂等键与事后校验是「出事能排查」的前提。这三条在任何档位都没有妥协空间，降档只能放宽前置断言。

## 9.3 幂等键

- 幂等指纹 MUST 由 server 依据业务参数生成，agent 完全不感知。
- tool MUST NOT 向 agent 暴露幂等键参数。
- MUST NOT 接受客户端传入的幂等键覆盖 server 生成的指纹。

> agent 是非确定性系统，重试时未必生成同一个键，幂等随即失效。要求 agent 复用键，等于把保障机制建在「模型行为可靠」这个假设上，与「不依赖特定模型特性」直接冲突。

- 实现 MAY 参考通用的幂等键机制（键唯一、不得在负载不同的请求上复用、推荐随机标识符），但 MUST NOT 绑定具体传输层字段。
- 指纹的计算范围 MUST 由实施方定义并文档化；具体哪些参数进指纹，由实施方定。
- 幂等窗口期 MUST 由实施方定义并文档化。

说明：时间戳、请求标识这类每次都变的参数不应进指纹，否则幂等永远不生效。采购单与库存调整的合理窗口期不同，这是业务判断，规范不代定。

## 9.4 前置断言

前置断言分两层，MUST 在实现和文档中写开：

| 层 | 内容 | 是否协议已覆盖 |
|---|---|---|
| schema 层 | 参数格式是否合法 | 已覆盖，协议要求 server 校验参数并以业务错误形式返回 |
| 业务状态层 | 当前状态是否允许此操作 | 未覆盖，这才是本规范所指的前置断言 |

**完成参数 schema 校验不构成满足前置断言要求。**

## 9.5 事后校验

事后校验同样分两层：

| 层 | 内容 | 是否协议已覆盖 |
|---|---|---|
| 返回值形状 | 返回结构是否符合声明的契约 | 已覆盖 |
| 写入是否落库 | 数据是否真的变成了期望的样子 | 未覆盖，这才是本规范所指的事后校验 |

**返回值符合 schema 不代表写入成功。**

说明：一个已知实现坑——错误响应不应被返回值契约校验，只有成功响应才校验。多个客户端侧校验器漏了这个判断，导致带结构化错误信息的 tool 直接不可用。

## 9.6 窄接口与可回滚批次

协议层无对应表达，按 server 实现约束执行。窄接口的依据是最小权限原则：每个 tool 只拥有完成其任务所需的最小权限，并限制其可执行动作的范围与类型。

## 9.7 人确认档的实现要求

- 确认动作 MUST 由 server 侧发起，MUST NOT 依赖客户端权限配置实现。

> 靠客户端配置实现的「确认」不是保障机制，是三个假设：假设接入方配对了、假设没人改配置、假设换 agent 时有人记得重配。三个假设在现场都不成立。协议层强制的东西验收时能测，客户端配置的东西测了也不算数。

- 客户端不支持 server 侧确认机制时，MUST 拒绝执行并返回可自纠的报错，MUST NOT 降级为直接执行。

说明：不写死会出现「支持的客户端弹窗、不支持的客户端静默执行」——它制造了「已经有确认机制」的错觉，而实际保护随客户端漂移，比统一不做更危险。

- 确认请求 MUST 展示完整的 tool 调用参数，MUST NOT 只给 tool 名称或摘要。

说明：只给名字的确认在审计意义上不构成确认，出事时无法证明用户知道自己批准了什么。

- server MUST NOT 用表单模式索取密码、密钥等敏感凭据，必须走跳转模式。
- server 发起的请求 MUST 只在处理某个客户端请求期间发出。

说明：保证每次确认都能追溯到用户或其 agent 主动发起的动作，不会凭空出现。这对可排查性是硬要求。

# 10. 自主度分级

**适用范围**：L2、L3。

## 10.1 三档

| 档位 | 含义 |
|---|---|
| 全自动 | agent 直接执行，无人介入 |
| 关键步骤人确认 | 执行前由 server 发起确认，人应答后继续 |
| 只出 plan | agent 只产出执行方案，由人执行 |

## 10.2 判定依据

三条依据全部满足才能进全自动档，任一不满足即降档。**硬规则，不留例外。**

1. 是否可逆
2. 是否影响主数据
3. 有无客观判定标准

说明：留口子的方法论等于没有方法论。现场一定会把口子当默认。

依据 1 直接复用协议的破坏性声明字段，只读/写复用只读声明字段。依据 2、3 是业务语义不是协议语义，标准没有，也不该指望后续协议版本补上——这一点写明，避免协议出新字段又要重新对齐。

## 10.3 判定示例

本规范 MUST NOT 给出「动作—档位」对照表，只给推导过程。

说明：一旦逐个动作指定档位，规范就退化成某个系统的操作手册，换个后端不成立。实施方照着推导过程推，推错了是判定问题，不是规范缺失。

说明：以「主数据归一」这个动作走一遍——① 可逆性：归一后原始的多个标识被合并，若无完整回滚批次则不可逆，依据 1 不满足；② 主数据：该动作的产物就是主数据本身，依据 2 不满足；③ 客观判定标准：两条记录是否指同一实体，在头部数据上可判、在长尾上无客观标准，依据 3 部分不满足。三条中有两条明确不满足，因此该动作落在「只出 plan」档。

## 10.4 档位归属由谁定

具体某个操作归哪一档，由实施方按自身业务风险判定，本规范不规定。读写不是阶段划分，是能力分级——实施方按自身风险承受度选做到哪一档。

# 11. 数据治理流程规范

**适用范围**：本次接入涉及数据治理时适用；不涉及则整章不适用，须在符合性声明中标注。

本章只定义流程骨架、每步产出物要求和验收口径。**执行方法不在本规范范围内。**

| 步骤 | 产出物 | 验收口径 | 由谁验收 |
|---|---|---|---|
| 1. schema mapping | 每张源表一份字段语义映射 | 每个字段的含义、单位、口径均有明确答案，无「待定」 | 源表的业务归属方 |
| 2. 事件流归约 | 统一格式的事件流，保留来源表与来源行标识 | 任一条事件可追溯回原始文件的具体一行 | 数据负责人 |
| 3. 主数据归一 | 归一后的主数据表 + 未归一清单 | 归一结论逐条经人工确认，未归一项显式标记 | 业务负责人 |
| 4. 覆盖率标注 | 覆盖率数值及其计算口径 | 口径可复算，与第 13 章定义一致 | 数据负责人 |

- 每步的验收方 MUST 在接入方案中明确到人，MUST NOT 只写角色。

说明：治理产出物的正确性只有业务方能判，技术方判不了。不落实到人，这一步会变成「谁都签了字，谁都没看」。

# 12. 接入验收流程规范

整条链：源码 → 出题 → 冻结 → 实现 → 跑题 → 改接口重跑。

## 12.1 出题隔离

- 出题 MUST 先于实现。
- 出题会话 MUST 只提供两样输入：后端源码/数据模型、本规范第 8 章。MUST NOT 提供 MCP server 代码。
- 题目产出后 MUST 先冻结（打标签、入版本库），再启动实现。
- 实现会话的工作目录 MUST NOT 包含题目文件。

说明：不冻结，实现过程中「顺手改一下题目」必然发生，而且发生时没人觉得自己作弊。

## 12.2 题目构成

- 每道题 MUST 包含完整三段：初始数据状态、自然语言指令、期望终态。缺初始态则终态无法判定。
- 初始数据 MUST 在出题时一并生成（基于 schema 造合成数据），MUST NOT 在接入时现取。
- 期望终态 MUST 写成可执行断言（哪些记录的哪些字段应变成什么），MUST NOT 写成自然语言描述。
- 写操作题 MUST 配初始态快照与重置脚本。

说明：每道写入题跑完数据库即脏，没有重置就只能跑一次，回归无从谈起。

## 12.3 生成方法的覆盖下限

L2、L3 接入以下三条全部为 MUST；L1 接入只适用第 1 条的只读部分。

1. 每个**写操作 tool** 至少 1 题。只读 tool 不设下限（SHOULD 覆盖）。
2. 实施方**实际启用的**每个档位各至少 1 题。未启用的档位不要求出题。
3. 必须含失败路径题，五类各至少 1 题：

| 类别 | 检验什么 |
|---|---|
| 参数缺失 | agent 能否根据报错自纠 |
| 前置断言不通过 | 同上 |
| 幂等冲突 | 同上（同一业务意图连续调用两次，断言终态只发生一次变更） |
| 越权 | 权限模型配置是否真实生效 |
| 声明与实现不一致 | 声明是否属实（如声明幂等的 tool 必须含重复调用场景） |

题目总数不设上限或下限，由实施方按业务复杂度自行拿捏。

说明：不定覆盖下限，「接入完成后能通过验证任务集」这条判据可以被一道题满足，等于没有判据。越权这一类不能省——它是唯一会真正造成损失的失败路径，而且第 7.2 节要求配置的权限模型，若验收侧完全不碰，等于从未验证过。

## 12.4 验收环境

- 接入方 MUST 提供独立验收环境，与生产环境数据隔离，支持数据库重置到指定快照。
- 验收测试 MUST NOT 在生产环境执行。

> 写成禁止式而非建议式：现场压力大时「在生产上跑一下试试」是很自然的想法，后果是不可逆的数据损坏。

说明：合成数据只用于验收环境，不进生产；验收环境的 schema 须与生产一致，否则断言不成立。

## 12.5 验证环节

- MUST 用通用 agent、不改 prompt 跑题。
- MUST NOT 使用出题那次的会话上下文跑题。

说明：出题 agent 知道自己的意图，必然通过，属于自证。

- 生成验收标准的 agent（工具）与被验收的 agent（被测对象）MUST 分离。前者 MAY 指定具体产品，后者 MUST 是通用 agent。
- 验收标准 MUST 客观可判定，MUST NOT 接受 agent 自评。

| 形式 | 是否合格 |
|---|---|
| 执行后某几条记录应变成什么样 | 合格 |
| 由 agent 判断本次操作是否合理 | 不合格 |

- 冻结后 MUST 先做一次可解性验证，确认题目自洽、数据对得上。
- 可解性验证 MUST 只查题目本身，MUST NOT 因为 agent 做不出来就改题。

## 12.6 迭代纪律

- 跑不通时 MUST 改 tool 定义，MUST NOT 改题目。

> 题目代表业务真实需求，tool 是可调的那一侧。反过来改，等于让需求迁就实现。

- 唯一允许改题的情况：题目描述的业务行为本身不符合后端实际业务语义。此时 MUST 留记录说明原因。

# 13. 指标口径

只定义两个指标。本规范只定义口径，MUST NOT 定阈值——阈值由实施方按业务定。

## 13.1 agent 调用成功率

- 口径：给定自然语言问题，选对 tool、参数正确、轮次合理的比例。
- 问题来源：按第 12 章方法生成并冻结的验证任务集。
- 该指标仅在**同一接入、同一冻结版本任务集**内跨迭代可比。跨接入横向比较无效，MUST 写入口径说明。
- 任务集重新生成或修改后，历史数据作废，MUST NOT 与新数据混用。

说明：不写死可比范围，现场一定会拿两个项目的数字比，而且一定会拿去汇报。

## 13.2 数据覆盖率

- 口径：归一后的主数据覆盖了多少比例的业务量。
- 性质：SHOULD 采集，非符合性必需。仅在涉及数据治理时适用。

# 14. 符合性判据

一次接入是否符合本规范，只看两条：

1. 换一个没接触过该后端的人，拿本规范加该系统的改造 PRD，能独立完成接入。
2. 接入完成后，由实施方用 coding agent 基于后端源码与 MCP server 定义生成验证任务集；通用 agent 在不改 prompt 的情况下完成这些任务，且终态数据与期望一致。

判据 2 的强度随符合性等级变化：L1 只验证读取与分析任务；L2、L3 须覆盖第 12.3 节的全部下限要求。

谁去跑、跑出什么结果，由实施方对齐，不在本规范范围内。

# 附：本规范不规定什么

以下内容由实施方或具体系统的改造 PRD 定义，本规范一律不涉及：

- 库表结构、字段清单、接口路径、请求响应格式
- 技术选型、架构方案、部署方式
- 具体业务数据的清洗过程与分析结论
- 某个具体动作归哪个自主度档位
- 任何指标的阈值
- 具体的验收题目
- 幂等指纹的参数范围与窗口期数值
- tool 命名采用前缀式还是后缀式
